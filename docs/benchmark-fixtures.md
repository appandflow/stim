# Benchmark fixtures

Fixtures live outside this repository, in repositories the benchmark root points
at. This page specifies the two that do not exist yet, the bare React Native app
and the Exact app, and what the harness reads from each. The standalone native
fixtures (Xcode, SwiftPM, Gradle) are generated by
`scripts/agent-benchmark/native-fixtures.mjs` and need no external repository.

A benchmark root serves one fixture kind. Use a separate root for the bare React
Native fixture and for Exact; the golden state, targets and results of a root
belong to its fixture.

## Bare React Native fixture ("Trailhead bare")

The harness is written against Trailhead, the Expo fixture. The bare fixture is
the same app on a bare React Native project, so the harness reads the same
names. It needs no Expo packages.

Create a repository containing:

- A bare React Native project (react-native-community CLI layout, `ios/` and
  `android/` committed, no `expo` or `expo-*` dependency, Metro from
  `@react-native/metro-config`). Use the React Native version of Trailhead's
  current Expo SDK, and one whose iOS template `AppDelegate.swift` assigns
  `window = UIWindow(...)` (0.77 or later); the native-change task inserts its
  line after that assignment.
- iOS: scheme and product `Trailhead`, bundle id `com.appandflow.trailhead`, so
  the app runs as `Trailhead.app/Trailhead`. Pods installed and committed
  `Podfile.lock`.
- Android: application id `com.appandflow.trailhead`, an `app_name` string in
  `android/app/src/main/res/values/strings.xml`.
- `app/_layout.tsx` exporting `export default function RootLayout() {`, the root
  component the entry file mounts. The error-fix task injects its render crash
  as the first line of that function.
- A bottom tab bar with a tab labelled `Settings`. `app/(tabs)/settings.tsx`
  renders a row titled `Offline maps` with
  `subtitle="Keep map tiles for saved trails on device"` as written in that
  file. The app may show an onboarding screen first; the proof sequence handles
  it.
- `.stim.json` only if Trailhead has one.

Pins, in the bare root's `pins.env`, beside the usual keys (`STIM_VERSION`,
`AGENT_DEVICE_*`, `IOS_*`, `ANDROID_*`, `COCOAPODS_VERSION`, Node, Xcode):

```text
FIXTURE_KIND=bare
BARE_FIXTURE_COMMIT=<40-hex commit of the clean checkout>
```

Then set `STIM_BENCH_FIXTURE` to that checkout, write `targets.json` for the
`ios|android` x `javascript|native|launch-crash` x arm keys, and run `preflight`
and `prepare` per platform as for Trailhead. Until `BARE_FIXTURE_COMMIT` is set
dispatch refuses the bare cells and names it.

What this validates is untested here: the harness's proof strings and watchers
have only run against Trailhead. Run the driver self-tests and one untimed pilot
cell per platform before the campaign.

## Exact fixture

Exact apps (the `exact.mjs` launcher next to `app.json`) are built by
`./exact.mjs ios --no-install`, which Stim also runs; the control arm uses that
command directly. The Exact integration is changing, so the fixture is pinned by
commit and described, not generated.

Create a repository containing an Exact app that implements the same
acceptance contract as the generated native fixtures, so the task prompt and
source proof apply unchanged:

- One source file contains the literal `native-revision-one`, shown on screen as
  text. The task replaces it with a run marker; no other line may need to change.
- The screen also shows `Count: 0` and an `Increment` button that adds one.
- iOS only. No declared native modules in `app.json` (keeps the build local and
  reproducible).
- A startup path where one added statement makes the app crash with the message
  visible in the platform log (the Exact host's Rust entry point, or its
  TypeScript entry, whichever the app's startup code is).

`native/exact-ios/fixture.json` in the benchmark root describes it:

```json
{
  "platform": "ios",
  "framework": "exact",
  "fixtureDirectory": "/abs/path/to/clean-checkout",
  "fixtureCommit": "<40-hex>",
  "source": "path/to/file-with-native-revision-one",
  "product": "<app product name>",
  "bundleId": "<bundle id>",
  "crash": { "source": "path/to/startup-file", "anchor": "fn app_start() {", "language": "rust" }
}
```

`crash.anchor` is a line that occurs exactly once in `crash.source`; the setup
inserts the crash statement on the line after it (`panic!` for `rust`,
`throw new Error` for `typescript`). Add `EXACT_FIXTURE_COMMIT=<same commit>` to
`pins.env`. The driver reads this file with
`node scripts/agent-benchmark/native-driver.mjs prepare|dispatch|collect exact-ios ...`.

## Launch-crash design for platforms without JavaScript

The error-fix task is the one the React Native rows use: "The app fails on
launch. Reproduce it and capture the runtime error before inspecting application
source, fix it, and verify the repair." The coordinator commits the crash to a
fixture checkout before dispatch, and neither the category nor the token appears
in the prompt.

| Platform                        | Injected change                                                                             | Where the error surfaces                                                      |
| ------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Standalone iOS, macOS (SwiftPM) | `init()` in the SwiftUI `App` struct that calls `NSLog` and `fatalError` with the run token | unified log, `simctl launch --console`, stderr of the macOS binary, Stim logs |
| Standalone Android              | `throw IllegalStateException(token)` after `super.onCreate` in `MainActivity`               | logcat `FATAL EXCEPTION` with the token and the file and line                 |
| Exact iOS                       | `panic!` or `throw` after the fixture's anchor line                                         | the Exact host log                                                            |

The token is `launchCrashToken(runId)`, the same value format as the JavaScript
crash. Proof: the token appears in command output before any command names the
source file (`nativeCrashReproduced`), the source equals the original byte for
byte afterwards (`launchCrashRepair`), only that file differs from the crash
commit, then the existing screenshot and process-identity proof. An injected
native crash changes native source, so each arm builds once more after the fix;
both arms start from the same warm outputs.

The Swift injection was type-checked with `swiftc`. Kotlin and Exact injection,
and whether the logs surface the token, are validated only by a first real run.
