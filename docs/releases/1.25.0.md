# 1.25.0

Stim Desktop and the Stim phone app ship through their own workflows; this release covers the twelve npm packages (`@stim-cli/core`, `@stim-cli/cache`, `@stim-cli/cache-s3`, `@stim-cli/agent-driver`, `@stim-cli/agent-driver-agent-device`, `@stim-cli/metro`, `@stim-cli/expo-build-cache`, `stim`, `@stim-cli/ci`, `@stim-cli/transport`, `@stim-cli/transport-tailscale` and `@stim-cli/server`). No package publishes for the first time in this release. Commits that only changed those apps, tests, CI or internal structure are not listed.

## New

- **Offloaded builds and worker peer artifacts compare a Stim build compatibility version instead of the exact Stim build (stim-server feature `build-compat`).** Before, a client and a build worker had to run byte-identical Stim builds, so an npm release on one Mac and a checkout build on the other, or any two different commits, could not offload to each other. Each `stim` now carries `STIM_BUILD_COMPAT` (1 in this release) in every toolchain it reports, and two machines that both report it build for each other when the values are equal. The value changes only in a release that changes what a worker builds, how it builds it, or the build and artifact messages. A client sends `compat` on `build.start`, and in place of `stimBuild` in React Native and SwiftPM peer artifact queries, only to a stim-server that advertises `build-compat`; against a server without it, peer artifact queries are skipped. A worker update that keeps the same compatibility version keeps its completed artifacts, and worker peer entries stored before this release miss once. A machine that reports no compatibility version still needs the exact same Stim build. Doctor and placement keep the `stim-build` problem code and its reason text, so Stim Desktop's update path is unchanged. The local build cache key does not change. Fixes [#4206](https://github.com/appandflow/stim/issues/4206). (`stim`, `@stim-cli/server`, `@stim-cli/core`) [91e3b90aa](https://github.com/appandflow/stim/commit/91e3b90aa0d9a5edcd409607af7aa611aeea45ad)
- **`ios.simslim` slims every Stim-owned iOS simulator without a profile per app.** The new setting takes `on` or `off`, default `off`, at every layer. With `stim settings set ios.simslim on --scope machine`, `stim ios` runs `simslim on` with SimSlim's default categories on each owned simulator it boots, adopts or finds already running, through the same path as a profile. On a simulator it boots, the mute runs after SimSlim's reboot. A project `ios.simslimProfile` still applies in place of the defaults, and `ios.simslim` set to `off` in a workspace, repo or committed layer opts that app out and restores stock services on a simulator Stim slimmed. The first slim reboots the simulator once, and a simulator that was already running stays unmuted after that reboot, as with a profile change (see the SimSlim mute fix below, and [#4250](https://github.com/appandflow/stim/issues/4250)). An already slim one is left alone. Without the `simslim` command, `stim ios` prints a one-line note and boots unslimmed, and `stim doctor` reports `ios.simslim is on, but SimSlim is not installed`. Hosted simulators on a named Mac are not slimmed. SimSlim's defaults disable push, StoreKit, iCloud, Safari sync and the Mail, Calendar and Contacts services among others, so an app that needs one should use a profile that keeps it, or `off`. Fixes [#4242](https://github.com/appandflow/stim/issues/4242). (`stim`, `@stim-cli/core`) [158350087](https://github.com/appandflow/stim/commit/158350087eeae363c3aae684c96ce44e3075b107)

## Fixes

- **An owned iOS simulator stays muted after SimSlim reboots it.** With an `ios.simslimProfile`, `stim ios` muted the simulator right after boot and printed `simulator muted`, then applied the profile with `simslim on`, which shuts the simulator down and boots it again. SpringBoard sets its default volume of 60 on that boot, so the simulator played sound. `simslim off` reboots the same way. Stim now mutes after SimSlim has applied or removed its profile, and waits up to 60 seconds for SpringBoard to finish starting first. When the wait fails or times out, the run prints `Could not mute this simulator` and continues. A simulator that is already running is still not muted, so a profile change on a running simulator leaves it at the volume SimSlim's reboot set. Fixes [#4229](https://github.com/appandflow/stim/issues/4229). [f41fc2b98](https://github.com/appandflow/stim/commit/f41fc2b983c5f7782d34e086e386e752ef8f0bc6)
- **Every package depends on the other Stim packages at the exact release version.** The 1.24.0 tarballs named internal dependencies such as `@stim-cli/core` as `^1.24.0`, so installing an older `stim` or `@stim-cli/server` could resolve a newer `@stim-cli/core` and run code from two versions together. From 1.25.0 every `stim` and `@stim-cli/*` dependency in the published manifests is the bare version, `pnpm run release:prep --check` accepts only `workspace:*` ranges, and the Release workflow refuses a packed manifest with a `^` or `~` internal range. Fixes [#4215](https://github.com/appandflow/stim/issues/4215). (every package with an internal dependency) [097cbc63c](https://github.com/appandflow/stim/commit/097cbc63c9f26834a19e9036438a2da9fd4b813a)
- **Launch verification waits while an Expo dev client's manifest request is pending.** An Expo dev client asks the dev server for its manifest before its bundle, and with the fingerprint runtime version policy Expo recomputes the fingerprint for every manifest request, so on a loaded machine a slow launch could end `launched: "unverified"` after the 20-second window. On Expo SDK 54 and later, where Stim injects its Metro config, Stim's Metro middleware now records each dev-client manifest request in `metro.ndjson` as `manifest_request_started`, `manifest_request_finished` or `manifest_request_failed` (debug level, with `platform` and `requestId`). Verification keeps waiting while one is in flight and for 15 seconds after one was served, up to 60 seconds after the launch. A manifest request is progress, not launch evidence: `true` and `"bundling"` still need the app's bundle request, and a failed manifest request extends nothing. Bare React Native, and Expo SDK 53 and older, keep the 20-second window. Fixes [#4207](https://github.com/appandflow/stim/issues/4207). [7c72fc4b9](https://github.com/appandflow/stim/commit/7c72fc4b99156b615237014f4a51e57954fed8ec)
- **The launch stability window ends once the app's JavaScript is running.** After the bundle response, verification waited a fixed 3 seconds before reporting the launch stable. It now ends half a second after the app's first `Running "<name>"` log for this launch, on iOS and Android, or at the 3-second cap. The verify line then reads `app JavaScript running -- the first screen may still be rendering` instead of `stable for 3s`. A fatal record or an exited process before the window ends still fails the launch; an error after it appears in `stim logs --errors`. Fixes [#4225](https://github.com/appandflow/stim/issues/4225). [c26b9cac0](https://github.com/appandflow/stim/commit/c26b9cac0784542d5e60562c4d9b8c09ee810ca6)
- **The Metro prefetch uses the bundle URL the app last requested.** On an Expo app, the prefetch during `stim ios` and `stim android` fetched the manifest to learn the bundle URL, which ran one more Expo fingerprint under the fingerprint runtime version policy and delayed the prefetch until it finished. The `bundle_response_started` record of an app's bundle request in `metro.ndjson` now carries its `url`, and the prefetch uses the newest recorded URL for the platform when it passes the same check as `metro.warmupUrl.<platform>` and its entry file still exists. Order: `metro.warmupUrl.*`, then the recorded URL, then the Expo manifest or the bare React Native default. A bare React Native app that has served a bundle also prefetches its recorded URL instead of the default index bundle. A workspace that has never served a bundle still fetches the manifest or uses the default once. Fixes [#4226](https://github.com/appandflow/stim/issues/4226). [65605ae9e](https://github.com/appandflow/stim/commit/65605ae9e96ede815a0e3cee986cbe2fc2494a2e)
- **`stim stop` shuts down a workspace's owned simulator and emulator concurrently.** It waited for each device's teardown before starting the next, so a workspace with both paid the simulator shutdown on top of the emulator's `adb emu kill`, which waits for the quickboot snapshot. The teardown itself, with its ownership re-checks, is unchanged. Results are still reported in the same order once every device has settled, so the `device` lines and the `stop --json` payload keep their order; progress lines can now come before them. When one teardown throws, the others still finish and are reported before the error propagates. Fixes [#4243](https://github.com/appandflow/stim/issues/4243). [ec621a003](https://github.com/appandflow/stim/commit/ec621a0036f34cdc0cd25996944e9595ffb238bf)
- **`stim ios` restarts a running simulator app with one `simctl launch --terminate-running-process`.** It ran a separate `simctl terminate` first. The `restarted running app (was pid N)` note and launch verification are unchanged. A dev client opened through a URL still terminates first, and Android is unchanged. Fixes [#4235](https://github.com/appandflow/stim/issues/4235). [03eee3e24](https://github.com/appandflow/stim/commit/03eee3e24cad4a56071aa74b7a2ef675207c8084)
- **`stim ios` lists simulators, runtimes and device types with one `simctl list --json` call.** A warm run made five `simctl list` calls before selecting a simulator. Boot, teardown and the ownership re-checks still list live. Fixes [#4228](https://github.com/appandflow/stim/issues/4228). [f7fa3baf5](https://github.com/appandflow/stim/commit/f7fa3baf5775e788ebdbb14f504ea758393489bf)
- **A build cache hit reuses the stored bundle id or Android package.** A cache entry now stores the app id read from its artifact, so a hit skips the `plutil` read of the bundle id on iOS and the `aapt` read of the package on Android. Entries stored before this release keep the read. Refs [#4209](https://github.com/appandflow/stim/issues/4209). [49526c12e](https://github.com/appandflow/stim/commit/49526c12e56eeeb231be4bc12961b84f467d310f)
- **`stim worktree warm` deletes known problem paths from copied directories instead of walking the whole copy.** After copying a directory it now checks only `.pnpm-store` and `expo-modules-jsi/apple/.DerivedData` inside `node_modules` (including pnpm's virtual store), and `android/build/generated/autolinking`. Whole ignored entries named `.jj`, `.pnpm-store`, `.DS_Store`, `.idea` or `.DerivedData` are still not copied, but `.DS_Store`, `.idea` and other `.DerivedData` directories nested inside a copied directory now stay in the copy. A delete whose parent resolves outside the copied entry, such as through a copied symlink, is skipped. Fixes [#4216](https://github.com/appandflow/stim/issues/4216). [2bd8c3281](https://github.com/appandflow/stim/commit/2bd8c3281f8423d80f038e152ca19026f6ba0c59)

## Migration notes

- **Update the client Mac and its build workers together.** A 1.25.0 machine and a 1.24.x machine never offload to each other: the older side reports no build compatibility version, so both fall back to the exact Stim build match, which differs. Doctor reports `stim-build`. Until both run 1.25.0, automatic placement builds locally, and a named build machine (`--remote-build <machine>`, `STIM_REMOTE_BUILD` or `remote.build`) refuses with `STIM_OFFLOAD_REFUSED`, as does automatic placement with `local` disabled in `remote.buildPoolDisabled`. Update a worker's service with `stim-server service update --release 1.25.0`. After that, later releases and checkout builds with the same compatibility version offload to each other.
- **Internal dependencies are exact pins.** `@stim-cli/expo-build-cache` or `@stim-cli/metro` installed beside a different `stim` version now brings its own copy of `@stim-cli/core` at its own version instead of sharing one through a `^` range. Nothing fails to resolve; the cost is a second `@stim-cli/core` on disk.
- **`metro.ndjson` has new records and fields.** `manifest_request_*` records appear in Expo workspaces' metro logs, and `bundle_response_started` gains a `url` field in every workspace. Readers of the log should ignore unknown events and fields.
