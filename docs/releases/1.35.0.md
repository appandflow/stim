# 1.35.0

Stim Desktop and the Stim phone app ship through their own workflows; this release covers the thirteen npm packages (`@stim-cli/core`, `@stim-cli/cache`, `@stim-cli/cache-s3`, `@stim-cli/agent-driver`, `@stim-cli/agent-driver-agent-device`, `@stim-cli/metro`, `@stim-cli/expo-build-cache`, `stim`, `@stim-cli/ci`, `@stim-cli/transport`, `@stim-cli/transport-tailscale`, `@stim-cli/transport-local` and `@stim-cli/server`). No package publishes for the first time in this release. The release was frozen at [16d378a87](https://github.com/appandflow/stim/commit/16d378a878cca30e1911426c0eee87da289df71f) ([#4556](https://github.com/appandflow/stim/pull/4556)). Every commit since v1.34.0 has an entry below. Stim Desktop 0.2.14 ships from the same release commit.

## New

- **A client without Xcode can build an iOS simulator Release app on a remote Mac.** `stim ios --configuration Release --remote <mac> --remote-build <mac>` used to refuse before asking the worker, because the iOS offload context marked every non-Debug configuration unsupported, and the refusal carried a pairing remedy that did not apply. The worker already compiles whatever configuration the job names, and its xcodebuild runs the bundle phase against the checkout the client synced, so the app it builds carries the client's current JS. The client installs a worker-built app as fresh and never runs the local JS swap on it; the cache entry holds the worker's bytes. A non-Debug React Native build never asks for a retained or peer-cached app, since such an app would carry its builder's JS: `reuseArtifact` and `cacheArtifact` are not sent, and no machine is asked for a cached app. A client without Xcode that has a local Release cache hit skips the swap with a plain note and rebuilds on the worker, an incremental build on a warm worker area. For an Expo Release offload the gitignored `.env.production` and `.env.production.local` are added to the synced files; an `EXPO_PUBLIC_` variable set only in the client's shell is not forwarded. Device builds still refuse a named machine, and the unsupported-build refusals now point to `--remote-build local` or `auto`. `STIM_BUILD_COMPAT` stays 2. `stim guide settings`, `stim guide lifecycle` and the website describe it. Fixes [#4542](https://github.com/appandflow/stim/issues/4542). A real Release cache hit on the worker needs a peer-cache protocol change and is tracked in [#4550](https://github.com/appandflow/stim/issues/4550). (`stim`, `@stim-cli/core`) [134eb716d](https://github.com/appandflow/stim/commit/134eb716d789b6ce4d885c1d27e9e22ff0111150)
- **Stim Desktop opens a paired machine's workspace in the regular workspace screens.** The separate paired workspace page is gone. A workspace owned by a paired machine now renders the same screen as a local one, with the stage line, git chip, device tiles, last and running build, Metro status and agents from the reported payload. Controls that cannot work are disabled with the reason: Stop and Reload App unless the pairing allows actions, and Run, build details, logs and Review Changes always. Nothing runs local `stim` against a path on another Mac. Fixes [#4555](https://github.com/appandflow/stim/issues/4555). (Stim Desktop) [16d378a87](https://github.com/appandflow/stim/commit/16d378a878cca30e1911426c0eee87da289df71f)

## Docs

- **The release process gates on Linux checks and runs the Windows suite after the publish.** The `Release` workflow keeps `tag-on-main`, `publish` and `smoke`. The full Windows unit suite moves to the new `Post-release validation` workflow, started by the same `v*` tag, so it cannot delay or fail the publish. The gate is the merge queue's `Merge gate` plus `test (node 22)`, `test (node 24)` and `published runtime (node 22.12.0)` from the push `CI` run on the release commit, matched by SHA. RELEASE.md, `docs/release-recovery.md`, `docs/e2e-and-ci.md` and `docs/testing.md` describe it. Fixes [#4552](https://github.com/appandflow/stim/issues/4552). [04492f6da](https://github.com/appandflow/stim/commit/04492f6da349419f1d4f0c5b9b84865365eea268)

## Migration notes

- **No worker update is needed for the Release offload.** It is client-side: a 1.34.0 worker already compiles `configuration: Release`, so only the client needs 1.35.0. `STIM_BUILD_COMPAT` stays 2, so 1.31.0 through 1.35.0 machines still offload builds to each other.
- **Release offload does not forward shell variables.** Put production `EXPO_PUBLIC_` values in `.env.production` or `.env.production.local` before offloading a Release build.
