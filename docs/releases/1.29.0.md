# 1.29.0

Stim Desktop and the Stim phone app ship through their own workflows; this release covers the thirteen npm packages (`@stim-cli/core`, `@stim-cli/cache`, `@stim-cli/cache-s3`, `@stim-cli/agent-driver`, `@stim-cli/agent-driver-agent-device`, `@stim-cli/metro`, `@stim-cli/expo-build-cache`, `stim`, `@stim-cli/ci`, `@stim-cli/transport`, `@stim-cli/transport-tailscale`, `@stim-cli/transport-local` and `@stim-cli/server`). `@stim-cli/transport-local` publishes its first real version in this release; its `0.0.0` placeholder only reserved the name. Commits that only changed those apps are not listed: [#4362](https://github.com/appandflow/stim/pull/4362) (the Stim Desktop tutorial, feature discovery and readability).

## New

- **stim-server and remote machines work over the local network, without Tailscale.** The new package `@stim-cli/transport-local` lets stim-server listen on the private IPv4 addresses that the new machine setting `server.lanAddresses` names, as addresses or interface names such as `en0`. The setting is empty by default, which means no listener, and wildcard, loopback, public and IPv6 entries are refused; the server log names each entry it cannot use. A running server applies a changed setting or a new DHCP lease within a few seconds, and the local `/health` reports `lan: { addresses, port }`. Connections are plain WebSocket on stim-server's own port (default 7787), authenticated and encrypted by the protocol 2 Noise handshake, with no TLS. `remote.machines` accepts `local:<host>[:<port>]`. When `server.lanAddresses` is set, `stim-server setup` checks the local network listener, prints the endpoints and the server's key fingerprint (also in `--json`), and warns when the macOS application firewall is on; it never changes the firewall. The client pins a `local:` worker's key only after a person confirms that fingerprint in `stim doctor --fix` in a terminal; until then the machine reports `key-unconfirmed` with the `fingerprint`, and Stim does not use it. A changed key reports `key-changed`. Offloaded builds work over the local network, as [#4458](https://github.com/appandflow/stim/pull/4458)'s run against a real worker showed; hosted Release and Debug runs on a simulator or emulator take the same path, but were not run over a local network on real machines. `stim-server pair` puts the first local network endpoint in the phone pairing code when Tailscale is not running and `server.lanAddresses` is set. Doctor reports the new diagnoses `lan-not-listening` and `lan-no-answer`. Part of [#3681](https://github.com/appandflow/stim/issues/3681). (`@stim-cli/transport-local`, `@stim-cli/server`, `@stim-cli/core`, `stim`) [ae5ac5540](https://github.com/appandflow/stim/commit/ae5ac5540c685aeb97aa22dfe10469495ba60f41)
- **Bounded pre-authentication handling on every network listener.** Before a client authenticates, each non-loopback listener (local network addresses and the Tailscale addresses stim-server already binds) holds at most 64 connections, 16 from one source address. It closes a socket that sends no request within 10 seconds, and turns an address away for a minute after 5 failed handshakes or 60 first contacts naming a pairing token or setup ticket it does not hold. Each listener has its own pool, so a flood on the local network address cannot refuse phones on the Tailscale address. The failure limiter forgets its oldest peer past 4096 entries. A phone connecting straight to a Tailscale address with `ws://` is now accepted; a browser page still cannot forge that origin, and a DNS-rebinding page is refused. `tailscale serve` peers arrive on loopback and are not affected. (`@stim-cli/server`) [ae5ac5540](https://github.com/appandflow/stim/commit/ae5ac5540c685aeb97aa22dfe10469495ba60f41)
- **`@stim-cli/core` exports for local machines.** `parseMachine` returns `transport` (`'tailscale'` or `'local'`) alongside `name` and `port`; `MachineTransport`, `DEFAULT_SERVER_PORT` (7787) and `localEndpoint` are new. A build or device-host machine credential's `transport` can be `'local'`, `BuildMachineReport` gains an optional `fingerprint`, and `MACHINE_CREDENTIALS_VERSION` stays 2. (`@stim-cli/core`) [ae5ac5540](https://github.com/appandflow/stim/commit/ae5ac5540c685aeb97aa22dfe10469495ba60f41)
- **Idle workspaces stop after `maintenance.idleStopHours`.** Automatic maintenance, in its idle check every `maintenance.idleCheckMinutes`, and `stim gc --delete` while `maintenance.mode` is not `off`, stop a workspace whose dev server runs or whose owned simulator or emulator is booted once it has had no real activity for `maintenance.idleStopHours`: 6 hours by default, `0` never. Real activity is a Stim command in the workspace (`start`, `ios`, `android`, `macos`, `web`, `reload`, `logs`, `worktree warm`), the end of its last native build, a Metro bundle or Expo manifest request or an HMR update, an agent-device command in its sessions, or a live view through stim-server. Device and app log lines, dev server output and maintenance's own records never count, so a simulator that only logs network chatter is idle. The stop is the one `stim stop` makes: the dev server stops, owned devices shut down through centralized teardown and are never deleted, the port is released, and device leases stay. The timeline's `supervisor_stopped` line names automatic maintenance and the idle time, and maintenance logs each stop and each workspace kept past the window with its reason (`stim logs --source maintenance`). Anything Stim cannot read or verify keeps the workspace, as do a build, a hosted or remote session, an unexpired device lease, a managed tunnel, a running owned Chrome and a dev server run through `metro.command`. A home redirected with `STIM_HOME` never idle-stops. To record HMR updates, the request shim watches Metro's `/hot` websocket and writes `hmr_update` to `metro.ndjson` at most once a minute, and the supervisor record in `state.json` gains `hmrUpdates: true` when its server loaded the shim. A driven device's `activity` in status JSON gains an optional `unknown` list of the checks that could not be read. Fixes [#4448](https://github.com/appandflow/stim/issues/4448). (`stim`, `@stim-cli/core`) [f836bea84](https://github.com/appandflow/stim/commit/f836bea842774edbd86dcbe081d0f3eee7fe2559)
- **`stim logs` counts as workspace use.** `stim logs` on workspace sources (not `--source gc` or `builds`) moves the workspace's `lastUsedAt`, which also feeds `gc --older-than`, idle worktree removal and device deletion age, and clears `workspace.hidden`. [f836bea84](https://github.com/appandflow/stim/commit/f836bea842774edbd86dcbe081d0f3eee7fe2559)

## Migration notes

- **Workspaces now stop on their own after 6 idle hours.** After updating, a workspace whose dev server or owned simulator or emulator has had no real activity for 6 hours is stopped as `stim stop` would stop it, the next time maintenance runs its idle check or `stim gc --delete` runs. Nothing is deleted, and the next `stim start`, `stim ios` or `stim android` starts it again. An agent that pauses longer than the window needs that command before it reads the app again. Change the window with `stim settings set maintenance.idleStopHours <hours> --scope machine` (fractions work, such as `0.5`), or for one workspace with `--scope workspace`; `STIM_MAINTENANCE_IDLE_STOP_HOURS` overrides both. Turn it off with `stim settings set maintenance.idleStopHours 0 --scope machine`, or keep one workspace running with `stim settings set maintenance.idleStopHours 0 --scope workspace` from that workspace. `maintenance.keep` does not keep a workspace from this stop. `maintenance.mode off` turns off the idle check and the stop in `gc --delete`.
- **Restart a dev server started before 1.29.0** with `stim stop; stim start` before relying on idle stop. A supervisor without `hmrUpdates: true` in `state.json`, which includes every one a 1.28.0 `stim` started, is always kept, because Stim cannot see its HMR updates. So is an Expo project before SDK 54, which cannot load Stim's Metro config adapter.
- **Maintenance defers idle stop on a busy Mac.** The idle check defers above `maintenance.maxLoadPerCore` (default 4) per core, so on a loaded machine a stop can wait until the load drops. `gc --delete` does not defer.
- **What a local network worker needs.** On the worker: stim-server 1.29.0, for example `stim-server service update --release 1.29.0`; `stim settings set server.lanAddresses '["<address>"]'` at machine scope, preferring an address to an interface name on a machine that moves between networks; on a Mac with the application firewall on, a person allows stim-server's `node` when macOS asks; on Linux, a firewall rule for TCP 7787 from the local network. Then run the `stim-server setup` command the client's doctor printed, which carries the setup ticket in `STIM_SETUP_TICKET` and `--port` when the entry names a port other than 7787; setup does not need Tailscale when `server.lanAddresses` is set. On the client: `stim` 1.29.0, the worker in `remote.machines` as `local:<host>` or `local:<host>:<port>`, and `stim doctor --fix` run twice, the second time in a terminal so a person can compare the fingerprint with the one setup printed and answer `y`. Without a terminal, with `--json` or on `n`, nothing is pinned and the machine stays `key-unconfirmed`. Copy the setup command only to the worker: the first machine to spend the ticket gets the approval.
- **What stays Tailscale-only.** Agent control of hosted apps needs a tailnet machine; a `local:` entry removes the agent grant and notes why. Stim Desktop's own pairing and Add Machine flows stay Tailscale-only, and Desktop shows a `key-unconfirmed` machine as Unknown. Desktop's server-side doctor never confirms a fingerprint. IPv6 local network addresses are not supported.
- **Older `stim` and local entries.** `MACHINE_CREDENTIALS_VERSION` stays 2, so a 1.28.0 `stim` skips a credential with `transport: 'local'`; it cannot use a `local:` entry. A `remote.machines` entry `local:<port>`, which used to name a tailnet host called `local`, now parses as a local network host.
- **A worker that does not set `server.lanAddresses` opens no new listener.** Its Tailscale listeners gain the pre-authentication limits above, and phones connecting straight to a Tailscale address with `ws://` are accepted. Update every Mac that runs stim-server with `stim-server service update --release 1.29.0` to get them.
- **Build offload is unaffected.** `STIM_BUILD_COMPAT` stays 2, so a 1.28.0 machine and a 1.29.0 machine still offload builds to each other over Tailscale. Hosted Debug runs still need client and worker on 1.28.0 or later.
- **New fields, no new state files.** The supervisor record gains `hmrUpdates`, `metro.ndjson` gains `hmr_update` records, maintenance records gain `check: 'idle'`, status JSON's device `activity` gains `unknown`, and doctor's build machine report gains `fingerprint`. All are optional, so older readers ignore them.
- **Stim Desktop's bundled server includes `@stim-cli/transport-local`.** stim-server imports it at start, so a Desktop build that bundles a 1.29.0 server must bundle the package too; `apps/desktop/scripts/server-runtime.mjs` does.

## QA

Skipping the pre-tag QA gate is the maintainer's standing default from 2026-10-26: releases skip it unless the maintainer asks for QA, and the maintainer did not ask for it for this release. This deviates from RELEASE.md section 3, which has no waiver for a stable version; the expedited RC lane is for prereleases only and was not used. This release took the full lane because it is the first that contains `@stim-cli/transport-local`. The waiver covers only section 3.
