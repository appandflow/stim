# 1.31.0

Stim Desktop and the Stim phone app ship through their own workflows; this release covers the thirteen npm packages (`@stim-cli/core`, `@stim-cli/cache`, `@stim-cli/cache-s3`, `@stim-cli/agent-driver`, `@stim-cli/agent-driver-agent-device`, `@stim-cli/metro`, `@stim-cli/expo-build-cache`, `stim`, `@stim-cli/ci`, `@stim-cli/transport`, `@stim-cli/transport-tailscale`, `@stim-cli/transport-local` and `@stim-cli/server`). No package publishes for the first time in this release. The release was frozen at [9b84e963e](https://github.com/appandflow/stim/commit/9b84e963e1edce3c4084e627b14818c0000a0393). Commits that change none of the npm packages are not listed: [#4497](https://github.com/appandflow/stim/pull/4497) (a protocol 2 Noise client and Keychain pairing store in Stim Desktop, with no user-visible change yet), [#4493](https://github.com/appandflow/stim/pull/4493) (a Linux owner fixture for the phone app's mock server) and [#4489](https://github.com/appandflow/stim/pull/4489) (the design for Desktop and phone pairing with owning stim-servers).

## New

- **Per-platform device caps.** Three machine settings cap one platform each: `concurrency.maxIosDevices` (`STIM_MAX_IOS_DEVICES`) for booted owned iOS simulators, `concurrency.maxAndroidDevices` (`STIM_MAX_ANDROID_DEVICES`) for booted owned Android emulators, and `concurrency.maxMacosApps` (`STIM_MAX_MACOS_APPS`) for hosted macOS apps on a worker. Each defaults to `0`, no per-platform limit, and they only tighten: a run must fit its platform's cap and `concurrency.maxDevices`. `maxDevices` still counts simulators and emulators together, local and hosted, and hosted macOS apps as a pool of their own. Local admission queues and reclaims for a platform cap the way it does for `maxDevices`; a run held back only by its own platform's cap does not hold up a run on the other platform, and reclaim for a full platform cap shuts down only devices of that platform. A stim-server worker applies all three caps when it offers and reserves a hosted session, counting its own local simulators and emulators. Local `stim macos` runs are not counted, so `maxMacosApps` limits hosted macOS apps only. A refusal names the full limit, such as `1 Stim iOS simulator(s) are already booted and concurrency.maxIosDevices is 1`, and hosted capacity refusals now end with the setting name, such as `(concurrency.maxIosDevices)`. `stim status` reports `capacity.platformDevices` while a cap is set, and `stim doctor`'s concurrency note names the caps. `stim guide settings`, `lifecycle`, `errors` and `macos` and the settings, remote machines, owned devices and commands website pages describe them. Fixes [#4482](https://github.com/appandflow/stim/issues/4482). (`stim`, `@stim-cli/core`, `@stim-cli/server`) [161bc98ca](https://github.com/appandflow/stim/commit/161bc98ca753902b25f944d88ab01ad0e0917d22)
- **A Linux machine can run the owning stim-server for the phone app.** A Linux machine that starts workspaces, such as a bot running `stim ios --remote <mac>`, can run `stim-server` as a systemd user service, and the phone app pairs with it to see its workspaces, offloaded builds and the hosted simulators it started. When no `tailscale serve` route reaches the server's port, or `tailscale serve status --json` cannot be read, `stim-server pair` and the server's startup line give its direct tailnet address, `ws://<tailnet IP>:<port>`, instead of assuming `wss://<name>:7443`. A server on a machine other than a Mac leaves the macOS-only features (Mac window capture, Xcode builds, physical iOS devices, `duo-frames`) out of its `hello` and no longer tries to build the `stim-frames` helper, and `stim status` no longer runs `simctl` off macOS. `stim-server pair --json` now prints the single-use and route notes on stderr, as plain `pair` does; stdout stays one JSON payload. `scripts/linux-worker/setup.sh` ends with the pairing command. The remote machines website page has a "Serve the phone app from Linux" section. Part of [#4487](https://github.com/appandflow/stim/issues/4487). (`@stim-cli/server`, `stim`) [0e6e4ff1d](https://github.com/appandflow/stim/commit/0e6e4ff1da37bccb87c26da6378646d51b8ad556)

## Fixes

- **Hosted agent control works when stim-server runs as a LaunchAgent.** On a Mac whose Tailscale is the macOS app, the app's CLI prints an error instead of JSON when `TERM` is unset, and a LaunchAgent has no `TERM`. Under `stim-server service install` every Tailscale call failed, so the server could not identify the tailnet node of a device-host client and refused every hosted agent request with `Forbidden.` (`agent-device open` failed at `lease_allocate`), and `stim-server service status` reported `tailscale: unavailable ... not JSON`. stim-server now runs every Tailscale CLI call (`status`, `serve status`, `serve`, `whois`) with `TERM=dumb` when `TERM` is unset, and keeps an existing `TERM`. When the server cannot identify the requesting node, the hosted agent route now answers `Forbidden. The server could not identify the requesting tailnet node.`; a node mismatch and a bad token still get the bare `Forbidden.`. Refs [#4500](https://github.com/appandflow/stim/issues/4500). (`@stim-cli/server`, `@stim-cli/transport-tailscale`, `@stim-cli/core`) [9b84e963e](https://github.com/appandflow/stim/commit/9b84e963e1edce3c4084e627b14818c0000a0393)
- **A failed `stim android` on a machine without an Android SDK no longer blocks `stop` and `worktree remove`.** On a client with no SDK, such as a Linux VM, `stim android` failed with `STIM_NO_DEVICE` and left an owned-device record, after which `stim android --remote <mac>` refused with `run stim stop first`, `stim stop` failed with `spawn emulator ENOENT` and `stim worktree remove --force` refused. The AVD reservation is now released when creation fails before `avdmanager` is spawned. Teardown treats a missing `emulator` binary on a machine with none of `ANDROID_HOME`, `ANDROID_SDK_ROOT`, `ANDROID_AVD_HOME`, `ANDROID_EMULATOR_HOME`, `ANDROID_USER_HOME` or `ANDROID_SDK_HOME` set as an unregistered AVD, so a record with no AVD data on disk clears and one with AVD data is kept; any of those variables keeps the old refusal, since it may name an unmounted volume. `stim android --remote` no longer counts that missing tool as a running local emulator. Fixes [#4490](https://github.com/appandflow/stim/issues/4490). [609633ff9](https://github.com/appandflow/stim/commit/609633ff95b4b4bab0ca5c8e70d3901cf2fb4b51)
- **Hosted app uploads are about 4 to 7 times faster.** The client sent one 32 KiB chunk per round trip and waited for each reply. It now keeps up to 64 chunks in flight, in offset order within each file, so the server's offset rule, digest check, resume and replay are unchanged. Measured from a fresh workspace to janics-mac-mini-2: a 203 MB Debug app from a Linux VM went from 234 s to 34 s, and a 179 MB app from a MacBook from 181 s to 42 s. The first failure stops new sends and is thrown as before. Fixes [#4286](https://github.com/appandflow/stim/issues/4286). [2b8725e00](https://github.com/appandflow/stim/commit/2b8725e0054029a8aa5bd3bd0c6fb8aac8644508)

## Migration notes

- **Existing device caps are unchanged.** The three per-platform settings default to `0`, so with them unset `concurrency.maxDevices` admits and refuses exactly as before, and hosted macOS apps stay capped at `maxDevices`. Per-platform caps only tighten: raising macOS above `maxDevices` means raising `maxDevices`. Local caps need `stim` 1.31.0 on that machine. A worker applies the caps to hosted sessions only after `stim-server service update --release 1.31.0` there. A 1.30.0 client works with a 1.31.0 worker and the other way round: the worker's per-platform local counts are removed from the offer before it reaches the client, so the stim-server protocol is unchanged. `capacity.platformDevices` is a new, additive field in `stim status --json`, present only while a per-platform cap is set.
- **Workers need the stim-server update for the hosted agent fix and the Linux owning server.** The Tailscale fix runs in stim-server, so a Mac that hosts simulators for other machines and runs stim-server as a LaunchAgent with the Tailscale macOS app needs `stim-server service update --release 1.31.0` before hosted agent control (`agent-device` with the session's `remoteConfig`) works; `stim-server service status` then reports the tailnet instead of `tailscale: unavailable ... not JSON`. Clients need no update for it. A Linux machine that serves the phone app needs `@stim-cli/server` 1.31.0 for the direct pairing address and the reduced `hello` features.
- **`stim-server pair` can give a `ws://` address.** On any machine, Linux or Mac, whose port has no `tailscale serve` route, or whose serve status cannot be read, a new pairing payload's endpoint is now `ws://<tailnet IPv4>:<port>` (7787 by default) instead of `wss://<name>.<tailnet>.ts.net:7443`, which nothing served. The client must reach that port over the tailnet directly, so a tailnet policy that allows only the serve port needs the serve route (`stim-server service install --serve`, or the `tailscale serve` command the note prints). A server with a serve route still gives `wss://`. Devices that are already paired are not affected. `pair --json` now writes its notes to stderr, so a script that expected empty stderr from it sees them there.
- **The faster upload needs only the client.** Any stim-server already answers requests in order, so a 1.31.0 client uploads pipelined to a 1.30.0 worker.
- **Build offload is unaffected.** `STIM_BUILD_COMPAT` stays 2, so 1.30.0 and 1.31.0 machines still offload builds to each other.
- **New settings and fields, no new state files.** The three `concurrency.*` settings and `capacity.platformDevices` are new; nothing else on disk changes.
