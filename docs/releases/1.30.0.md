# 1.30.0

Stim Desktop and the Stim phone app ship through their own workflows; this release covers the thirteen npm packages (`@stim-cli/core`, `@stim-cli/cache`, `@stim-cli/cache-s3`, `@stim-cli/agent-driver`, `@stim-cli/agent-driver-agent-device`, `@stim-cli/metro`, `@stim-cli/expo-build-cache`, `stim`, `@stim-cli/ci`, `@stim-cli/transport`, `@stim-cli/transport-tailscale`, `@stim-cli/transport-local` and `@stim-cli/server`). No package publishes for the first time in this release. Commits that only changed repository automation are not listed: [#4466](https://github.com/appandflow/stim/pull/4466) (the QA matrix classifies `vitest.global-tmpdir.ts` as test configuration). The release was frozen at [9555fb2ec](https://github.com/appandflow/stim/commit/9555fb2ecd4b0089da78807af9494c245feb174d), but the merge queue landed [#4470](https://github.com/appandflow/stim/pull/4470) and [#4472](https://github.com/appandflow/stim/pull/4472) on `main` ahead of the version commit, and [#4474](https://github.com/appandflow/stim/pull/4474) and [#4479](https://github.com/appandflow/stim/pull/4479) ahead of the first notes correction, so the tagged release contains them and they are listed here. [#4479](https://github.com/appandflow/stim/pull/4479) only changes a test: the idle stop tests stub the host load check, so they no longer fail on a loaded machine ([#4462](https://github.com/appandflow/stim/issues/4462)).

## New

- **iOS builds and hosted simulators from a client without Xcode.** A Linux or Windows client with no Xcode and no simulator SDK can now offload an iOS simulator Debug build of a React Native or Expo app to a paired Mac approved for builds, and run it on a simulator that Mac hosts, with `stim ios --remote <mac> --remote-build <mac>`; Metro stays on the client. The worker's Xcode, simulator SDK and CocoaPods are the build's toolchain: offload still requires a Mac with Xcode, a simulator SDK and the runtime, and keeps the build compatibility, CPU and Bundler checks, but no longer compares the client's Xcode, simulator SDK or CocoaPods version, which it does not have. A client that has an Xcode still needs the same one as the worker. The client skips its own `pod install` and leaves it to the worker; prebuild still runs on the client. `stim doctor` on a non-Mac host judges remote Macs for the iOS app of a project with an `ios/` directory or an Expo app, without comparing the client's CPU, and its iOS note names the paired-Mac route next to EAS. Native Xcode apps without React Native still need Xcode on the client. Fixes [#4460](https://github.com/appandflow/stim/issues/4460). [9555fb2ec](https://github.com/appandflow/stim/commit/9555fb2ecd4b0089da78807af9494c245feb174d)
- **`stim device location`, `permission`, `push` and `network`.** Four subcommands change this workspace's own simulator or emulator without its UDID or serial: `stim device location <ios|android> (--set <lat,lng> | --clear)`, `stim device permission <ios|android> <grant|revoke|reset> <service>`, `stim device push ios --payload <json>` and `stim device network android <on|off>`, each with `--slot` and `--json`. The target is the slot's owned, booted simulator or emulator, checked the way `reload` checks it; a hosted device, an EAS Simulator session, a physical device or a device Stim does not own refuses with the new `STIM_DEVICE_TOOL_TARGET` before any tool runs. An action the platform lacks (clearing an Android location, an iOS network switch, an Android push) refuses with `STIM_DEVICE_TOOL_UNSUPPORTED`, and a failed `simctl` or `adb` call, or a device that does not report the change afterwards, with `STIM_DEVICE_TOOL_FAILED`. `--json` prints one line with a `readBack` of what the device reported for Android permissions and Android network, and `null` for iOS location, permissions and push and Android location, where the platform has no read. `stim guide lifecycle`, `stim guide errors` and the commands website page describe them. Refs [#4461](https://github.com/appandflow/stim/issues/4461). [c026360c3](https://github.com/appandflow/stim/commit/c026360c3280e838f8455995f10e36a5aba761a0)
- **Hosted simulators and emulators are muted.** A Mac that hosts simulators and emulators for other machines now mutes each one it boots or adopts, as a local boot does: an iOS simulator through `devicectl ... audio --volume 0` once SpringBoard is up, and an Android emulator's media volume (Android 15 and later), both read back. The mute is best effort: a failure is neither reported to the client nor recorded, and never fails the hosted run. Only Stim-owned devices are touched, never the host's own volume, and hosted simulators are still never slimmed. This runs in the worker's stim-server. Fixes [#4278](https://github.com/appandflow/stim/issues/4278). (`stim`, `@stim-cli/server`) [6b6dcc23a](https://github.com/appandflow/stim/commit/6b6dcc23a351388790239a093edbad926a85453a)

## Fixes

- **`stim logs` no longer waits on hosted device log copies it cannot use.** A query that cannot return device records, such as `--source metro`, `--source client` or `--source build`, skips the copy of native logs from hosted iOS and Android slots, so it no longer waits for an offline host's connect timeout. A hosted macOS app's copy still runs for every source, because its records keep the host's own sources. `--errors` without `--source` is unchanged, and `--follow` still starts its hosted followers for every source. Part of [#4281](https://github.com/appandflow/stim/issues/4281). [2a255af8d](https://github.com/appandflow/stim/commit/2a255af8d8a45b6b9d74830d9d53ba8bdba9160d)
- **Hosted admission no longer refuses for reasons that do not describe the host.** An unreadable memory pressure sample is read once more before a hosted session is refused, and only a real `warning` or `critical` refuses at once; the messages say which it was (`Host memory pressure is <level>; hosted sessions wait until it is normal.` or `Host memory pressure could not be read; retry shortly.`). Hosted iOS and Android sessions are admitted once, at the offer, and their prepare, adopt and inspect steps no longer sample memory again, so an admitted session is no longer refused after it exists. Hosted macOS app sessions count against `concurrency.maxDevices` among themselves, apart from simulators and emulators, and skip the local device count. A hosted iOS session that is still preparing is no longer counted twice, as a session and as a local simulator. Capacity refusals read `Hosted device capacity is full: ...`, `Hosted macOS capacity is full: ...` or `Hosted device capacity is unknown: ...`. `@stim-cli/core` exports the new `hostedMemoryRefusal`. Fixes [#4274](https://github.com/appandflow/stim/issues/4274). (`@stim-cli/server`, `stim`, `@stim-cli/core`) [4bad94c3c](https://github.com/appandflow/stim/commit/4bad94c3cfde48051b6ea6596cc348564af8dbe7)
- **An iOS readiness probe that times out on a still-Booted simulator is retried.** After SpringBoard has started, `stim ios` probes the owned simulator with `simctl spawn <udid> launchctl list`. A probe that timed out used to refuse at once with `STIM_NO_DEVICE`, which happened on a loaded Mac, often right after `stim stop` and a reboot. Now a timed-out probe re-reads the simulator's state and is retried while it still reports `Booted`, or its state cannot be read, for about 3 minutes from the first probe; a simulator that leaves `Booted`, another error, or the end of that window still refuses with the same message. `stim guide errors` says so. Refs [#4467](https://github.com/appandflow/stim/issues/4467). [b0a8d6270](https://github.com/appandflow/stim/commit/b0a8d6270bedfcd50ba70ed247a7b30bc3d1633d)

## Migration notes

- **The hosted mute needs a stim-server update on each hosting Mac.** It runs in the hosted worker that ships with stim-server, so a Mac that hosts simulators or emulators for other machines mutes them only after `stim-server service update --release 1.30.0` there. Clients need no update for it.
- **Commit `Podfile.lock` before building iOS from a client without Xcode.** The worker runs `pod install` and fingerprints the checkout again before it compares with the client. When `pod install` changes fingerprinted files there, for example because no `Podfile.lock` is committed or it is stale, the build fails closed with `fingerprint-mismatch`. Run `pod install` once on a Mac and commit what it changed, including the CocoaPods-integrated Xcode project. The client needs `stim` 1.30.0; the worker needs no update for this, since the build request is unchanged.
- **No peer artifact reuse for a client without Xcode.** Such a client sends no peer artifact query, so it never reuses an artifact another machine built; its own local build cache works as before.
- **Build offload is unaffected.** `STIM_BUILD_COMPAT` stays 2: `scripts/build-compat.json` was re-recorded for the client-side toolchain judging without a bump. A 1.29.0 machine and a 1.30.0 machine still offload builds to each other.
- **The hosted admission fixes also need a stim-server update on each hosting Mac.** The offer, the hosted iOS, Android and macOS workers and the capacity counts run in the worker's stim-server, so a hosting Mac admits sessions the new way only after `stim-server service update --release 1.30.0` there. A Mac that runs Stim Desktop test copies and hosted simulators together sees the most change: its macOS app sessions no longer take simulator and emulator slots, and each pool can now hold up to `concurrency.maxDevices`.
- **The new device tools act only on local devices.** `stim device location|permission|push|network` refuse a hosted device, an EAS Simulator session and a physical device. `push` needs the app to already hold notification permission on the simulator, which `simctl privacy` cannot grant. A permission the app does not declare cannot be changed.
- **No new settings, fields or state files.** The device tools' `--json` line and the three `STIM_DEVICE_TOOL_*` error codes are new output, not new state.
