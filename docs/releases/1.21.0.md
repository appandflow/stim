# 1.21.0

Stim Desktop and the Stim phone app ship through their own workflows; this release covers the twelve npm packages (`@stim-cli/core`, `@stim-cli/cache`, `@stim-cli/cache-s3`, `@stim-cli/agent-driver`, `@stim-cli/agent-driver-agent-device`, `@stim-cli/metro`, `@stim-cli/expo-build-cache`, `stim`, `@stim-cli/ci`, `@stim-cli/transport`, `@stim-cli/transport-tailscale` and `@stim-cli/server`). `@stim-cli/cache-s3`, `@stim-cli/agent-driver`, `@stim-cli/agent-driver-agent-device`, `@stim-cli/transport` and `@stim-cli/transport-tailscale` publish their first release. Commits that only changed those apps, tests or internal structure are not listed.

## Breaking: re-pair every device

**This minor release breaks pairing: stim-server speaks protocol 2 only, and no pairing, approval or credential from protocol 1 is carried over.** Every network connection to stim-server, loopback TCP included, now runs a Noise handshake before any request: a new client spends a single-use pairing token or setup ticket once, and from then on the server recognizes it by its own public key and the client accepts only the server key it pinned. There is no backwards compatibility in either direction: a protocol 2 stim-server refuses an older phone app, Stim Desktop or `stim` CLI with `protocol-unsupported` ("Update this app or Stim, then pair again"), and a protocol 2 client cannot talk to stim-server 1.20.2 or older. Stim Desktop and other clients of the same user on the same Mac no longer pair: they connect to the Unix socket `$STIM_HOME/server/local.sock` (mode 0600), which needs no handshake. (`@stim-cli/server`, `@stim-cli/core`, `stim`) [be8cb61ae](https://github.com/appandflow/stim/commit/be8cb61aeb7348921505dc3875c1ac6fc105b277), [8be0bc834](https://github.com/appandflow/stim/commit/8be0bc8342955b5809269ac83dae29bc32208c25)

What this means on disk: `server/devices.json` and the `*-clients.json` approval files from 1.20.2 are not read, and the first protocol 2 write replaces them, so going back to 1.20.2 afterwards loses them too. `server/secrets.json` stores each pairing token's or setup ticket's derived PSK and lookup, never the token, and `server/pairing.json` is no longer used. The client keeps its credentials for the machines in `remote.machines` in the same files, `build-machines.json` and `device-host-machines.json`, with a new schema; old entries are ignored, so remote builds and hosted devices on those machines stop until the machine approves this one again. Automatic placement falls back to a local build; a build named with `--remote-build <machine>` fails with `STIM_OFFLOAD_REFUSED`, and so does automatic placement when `remote.buildPoolDisabled` disables local builds.

Update every machine that runs stim-server or `stim` to 1.21.0 first, then re-pair. Only Stim Desktop 0.2.0 or later and the Stim phone app build released with 1.21.0 speak protocol 2: Stim Desktop 0.1.28 and older bundle a protocol 1 stim-server and make protocol 1 pairing codes and setup commands, so for Desktop users the steps below take effect once Stim Desktop 0.2.0 or later is installed. Stim Desktop 0.2.0 also requires `stim` and stim-server 1.21.0: once Sparkle installs it, a Mac whose `stim` CLI is still 1.20.2 cannot run stim from Desktop, local use included, until the CLI is updated (`npm install --global stim@1.21.0`). Update the CLI before or together with Desktop.

1. **Each Mac or machine running stim-server.** Update the server itself, on that machine. Stim Desktop's bundled server updates with Stim Desktop 0.2.0 or later. A service installed with `stim-server service install` updates with `stim-server service update --release 1.21.0` run on that machine (`npx --yes --package @stim-cli/server@1.21.0 stim-server service update --release 1.21.0` without a global install). A protocol 2 client cannot update a protocol 1 machine over the tailnet: remote update needs the machine's pinned server key from a protocol 2 approval.
2. **The phone app.** Install the Stim phone app build released with 1.21.0. It deletes its protocol 1 pairings on first launch. In Stim Desktop 0.2.0 or later, open the Phones page (if it is missing, turn on the **Phone app** flag under Settings > Advanced > Feature Flags), turn on **Serve to phones**, choose **Pair a Phone…** and scan the QR code. Without Desktop, run `stim-server pair --json` (`npx --yes --package @stim-cli/server@1.21.0 stim-server pair --json` without a global install) and enter its endpoint and token on the phone. The QR code carries the server key's fingerprint, which the phone checks before it pairs; manual entry carries no fingerprint. A phone that meets a server older than protocol 2 shows "Update stim-server on this Mac. It speaks an older protocol than this app.", and a QR code from an older server is refused with "This pairing code is from an older stim-server. Update stim-server on this Mac."
3. **Stim Desktop.** Install Stim Desktop 0.2.0 or later. Nothing to pair on its own Mac: it talks to its bundled server over the Unix socket. If a stim-server 1.20.2 already answers on Desktop's port, either a service from `stim-server service install` or the executable set as **stim-server executable** under Settings > Advanced, Desktop uses it and shows `This stim-server <v> is too old for this Stim Desktop. Update it, or clear the stim-server override in Settings.` Update it with `stim-server service update --release 1.21.0`, or clear that field. Then approve each remote machine again (step 4); Desktop's Add Machine wizard generates the command.
4. **Remote machines for builds and hosted devices.** Update the remote machine to stim-server 1.21.0 first (step 1). Then, on the machine that sends work, run `stim doctor --fix`, or use the Add Machine wizard of Stim Desktop 0.2.0 or later. For each machine in `remote.machines` it makes a new setup ticket and prints the command a person runs on that machine to approve it, in npx form with this `stim`'s own version:

   ```bash
   STIM_SETUP_TICKET=<ticket> npx --yes --package @stim-cli/server@1.21.0 stim-server setup --expires <ISO-time> --build --device-host
   ```

   It drops `--device-host` for a machine that is not a Mac, and on Windows the variable is set the PowerShell way (`$env:STIM_SETUP_TICKET=...`), as Stim Desktop's Add Machine command does. Setup updates an older service installed with `stim-server service install` in place, and refuses an older server it does not manage, such as one an older Stim Desktop runs, with an update remedy. `stim doctor` reports a machine as `not-asked` before any `--fix`, as `pending`, with the command printed again, after `--fix` until a person runs setup, and tells you when the machine's stim-server is older than protocol 2.

   A `stim` 1.20.2 client that reaches a 1.21.0 machine shows "This stim-server speaks protocol 2, with its own authentication. Update this app or Stim, then pair again." and builds locally instead.

5. **Scripts.** Pin `@stim-cli/server@1.21.0`, not an older version, in any `npx` command that pairs or sets up a machine: an older server prints protocol 1 pairing codes and setup that a 1.21.0 client cannot use.

## Removed (breaking)

- **Protocol 1 commands, flags and fields are gone** (see [Breaking: re-pair every device](#breaking-re-pair-every-device)). `stim-server devices grant <id>` takes only `--control` or `--read`; build and device-host access come only from `stim-server setup` with a setup ticket, and the pending access request flow and its Allow/Deny are removed. `stim-server setup` refuses `--client`: the ticket alone names the requesting machine. `stim-server devices --json` replaces `identity` with `from` (a label only) and `keyFingerprint`. `stim-server pair --json` prints `{ qr: { v: 2, name, endpoint, pairingToken, fingerprint }, expiresAt }` (without `--json`, the bare `qr` object), and the phone checks the server key's fingerprint. The tailnet health reply is only `{ "version" }`. The `hello` request drops `protocol` and `auth` and gains an optional `access` (`build` or `device-host`), its result drops `deviceToken` and `approval`, and the error codes `approval-pending` and `identity-unavailable` are replaced by `unknown-secret`. In `stim doctor --json` `remoteMachines` and `deviceHosts`, the state `node-changed` is now `key-changed`. (`@stim-cli/server`, `@stim-cli/core`, `stim`) [be8cb61ae](https://github.com/appandflow/stim/commit/be8cb61aeb7348921505dc3875c1ac6fc105b277)
- stim-server no longer runs a login shell to capture its environment. A variable that only a shell profile sets, such as a `STIM_*` variable or a private CocoaPods on `PATH`, reaches the server only through its own environment, `--env KEY=VALUE` or `--path-prepend <dir>`. (`@stim-cli/server`) [edaf8b54c](https://github.com/appandflow/stim/commit/edaf8b54c7f2dbda2752d83d2b5fc35fc44b0389)
- `stim-server setup` reads the setup ticket from the `STIM_SETUP_TICKET` environment variable and refuses `--ticket`, because other users on the machine can read command-line arguments. Setup removes the variable from its environment before it starts children. Stim Desktop's Add Machine command sets it, inside a PowerShell script block with `$env:` on Windows. (`@stim-cli/server`) [aafaa4f05](https://github.com/appandflow/stim/commit/aafaa4f05aa307ee89ae1d021c99b8d96fab235e)
- The programmatic API error code `STIM_WORKER_FAILED` and its `stim guide errors` entry are removed (see the in-process API item below). [8174f08a3](https://github.com/appandflow/stim/commit/8174f08a3fe54a6156c0e0eb45f718a87dc0ad84)
- The `eas` build cache tier runs fixed `eas-cli` commands (`fingerprint:generate`, `build:download`, `upload`) instead of loading the `eas-build-cache-provider` SDK into the Stim process. It needs `eas-build-cache-provider` in the app and `eas-cli` installed in the app or on `PATH`; without one the tier reports `the EAS build cache needs an installed eas-cli executable`, and Stim never installs it during lookup. A Windows `.cmd`/`.bat` launcher needs a project `eas-cli` so cancellation can stop Node directly. Fingerprint and transfer commands share one deadline per phase, and timeout or cancellation kills that phase's process. EAS authentication is cached per operation. [43f8f321f](https://github.com/appandflow/stim/commit/43f8f321f62d45b013ffabd953d4b788f784d874)

## New

- **`createStim().settings()` and `createStim().stats()` read settings and stats in the calling process.** `settings()` returns the `stim settings --json` payload: every setting with its effective value, origin and per-layer values. An invalid environment override rejects with `StimError` `STIM_BAD_ARG` and its remedy. `stats()` returns the `stim stats --json` payload, with the last recorded agent-device and SwiftPM cache usage instead of measuring it again. Both run in the calling process and accept `signal`; an aborted read kills its child processes and rejects with `STIM_CANCELLED`. `createStim` gains an `env` option (default `process.env`) that Stim reads its settings overrides and `STIM_HOME` from and passes to the operations it runs; the client's home is fixed at creation. New exported types `StimReadOptions`, `StimSettings` and `StimStats`. stim-server answers `settings.get` and `stats.get`, and reads the stats for machine details, through these calls instead of running `stim settings --json` or `stim stats --json`. [c00641db0](https://github.com/appandflow/stim/commit/c00641db03aa9c6208d9680e08ba9775258b3b42), [50548d4c4](https://github.com/appandflow/stim/commit/50548d4c4a5407194fdc87b2618fc75807daa2ee)
- `createStim().stop()` runs in the calling process instead of a worker. An aborted `stop()` finishes its teardown and then rejects with `STIM_CANCELLED`. An exception thrown by `onProgress` stops further progress and propagates unchanged: `build` and `run` are cancelled, and `stop()` or a read finishes its work first. [6d223b9cc](https://github.com/appandflow/stim/commit/6d223b9ccc2370864ffe6ec7e84957b7b0eb76d7)
- **stim-server serves view-shaped status subscriptions.** A server that offers them lists `status-views` in its `hello` features. `workspaces.subscribe` sends `workspaces` events with a `seq` starting at 0: the first carries `snapshot` (`{ workspaces, worktrees, archived }`, with each workspace trimmed to what a list needs and the 10 newest archives), and later events carry only `{ upsert, remove }` deltas by `path` and `archived` when it changed. A client that misses a `seq` subscribes again. `workspace.subscribe` with `{ workspace }` sends that workspace's full `environment`, or `null`. `machine.subscribe` sends `capacity`, `machine`, `deviceLeases`, `simctlAvailable`, `maintenance`, `usage` and `ownLeases`. `builds.history`, `archived.list` (optional `before` and `limit`, at most 50, returning `next`), `worktrees.list` and `maintenance.get` return the full data, waiting up to 30 seconds for the server's first status. `@stim-cli/core/state` exports the view derivation and keyed deltas, and `@stim-cli/core` the new protocol types. - **Automatic maintenance escalates through three disk pressure levels.** Level 1 is free disk under `budget.minFreeDiskGb` (20 GB), level 2 under the new `maintenance.urgentFreeDiskGb` (default 12), and level 3 under the new `maintenance.criticalFreeDiskGb` (default 6) or `budget.hardFloorDiskGb`, whichever is higher. 0 turns `maintenance.urgentFreeDiskGb` or `maintenance.criticalFreeDiskGb` off; level 3 still applies below `budget.hardFloorDiskGb`. At levels 2 and 3 the protection window is the new `maintenance.pressureProtectMinutes` (default 10) instead of `maintenance.protectRecentHours`. Level 2 clears build outputs of workspaces unused for that window, parked simulators and emulators, and the build directories of idle worktrees (`ios/build`, `android/app/build`, `android/build`, `android/.gradle`, `.build`). Level 3 empties the Swift compilation cache, removes finished worktrees with the short window as grace, stops the dev server of otherwise inactive workspaces and deletes their owned devices, and deletes `node_modules` and `ios/Pods` of idle linked worktrees, never the source checkout. Each step re-measures and stops once free disk is back above its level's floor. A directory is cleared only when git tracks nothing in it and nothing under it, nor the worktree's index, HEAD or Stim state, changed within the window. `stim status` shows the level, `status --json` reports `pressure.diskLevel`, and every command prints one stderr line while the last check, at most 10 minutes old, measured level 3. Running dev server supervisors now trigger the disk check each minute. ## Migration notes

- Re-pair every phone and approve every remote machine again, after updating each machine's stim-server to 1.21.0: see [Breaking: re-pair every device](#breaking-re-pair-every-device). Update the machines first; a phone app or `stim` 1.21.0 cannot pair with stim-server 1.20.2.
- Do not downgrade a machine to 1.20.2 after 1.21.0 has written its pairings: the protocol 1 records are gone, and it would need pairing again too.
- A `STIM_*` variable or tool path that only your shell profile sets no longer reaches stim-server. Pass it with `--env KEY=VALUE` or `--path-prepend <dir>`, or set it in the service's environment.
