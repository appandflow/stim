# 1.24.0

Stim Desktop and the Stim phone app ship through their own workflows; this release covers the twelve npm packages (`@stim-cli/core`, `@stim-cli/cache`, `@stim-cli/cache-s3`, `@stim-cli/agent-driver`, `@stim-cli/agent-driver-agent-device`, `@stim-cli/metro`, `@stim-cli/expo-build-cache`, `stim`, `@stim-cli/ci`, `@stim-cli/transport`, `@stim-cli/transport-tailscale` and `@stim-cli/server`). No package publishes for the first time in this release. Commits that only changed those apps, tests, CI or internal structure are not listed.

## New

- **`device-host.metro.ports` (feature `hosted-metro-ports`): a hosted iOS Expo dev-client run picks a Metro port that is free on both Macs.** An Expo dev client loads its bundle from the port that the client's dev server writes into the manifest, so the hosting Mac's session bridge has to listen on the client's Metro port (see the matching Fixes entry). Both Macs allocate Metro ports upward from 8082, so binding the bridge on the client's port would often be refused with `STIM_HOSTING_REFUSED` at `device-host.metro.open`, after the build and the simulator boot, because the host already uses that port. Before it starts Metro for an Expo app that has an `expo-dev-client` dependency on a hosted iOS Debug run (named host or auto placement), `stim` now asks the host which of a window of 64 candidate ports already accept loopback connections (`{ ports }` in, `{ busy }` out, at most 256 ports, device-host approval only) and reserves a port that is free on both. A recorded workspace port the host uses is moved with the existing "Reserved port N for this project instead" note. A Metro that is already running, or a `metro.port` / `STIM_METRO_PORT` pin, is never moved: if the host uses that port the run refuses with `STIM_HOSTING_REFUSED` before the build, a pinned Metro is not started, and the remedy says to run `stim stop`, then `stim ios --remote <machine>` without `stim start`, or to pin a port free on both Macs. Ports held by the same client's own dev-client bridges are not reported busy, so a rerun against a resumed session does not conflict with itself. When the host does not advertise `hosted-metro-ports` or cannot answer, the run treats every port as free, picks one free on this Mac and notes that it could not check the host; the host's own bind check still refuses an occupied port. Fixes [#4096](https://github.com/appandflow/stim/issues/4096). (`stim`, `@stim-cli/server`, `@stim-cli/core`) [f075a6acf](https://github.com/appandflow/stim/commit/f075a6acf9703518c19fcfebe1fa7db6cb6ac4d2)
- **`remote.easMaxDurationMinutes` (machine setting, positive integer, default 30) caps each EAS Simulator session Stim creates.** Stim passes it to `eas sim` as `--max-duration-minutes` for `--remote eas` and `remote.easFallback`, so EAS stops the session and stops billing after that many minutes even when nobody ran `stim stop` (for example when the workspace was deleted by hand). Before, Stim never passed the flag, so a session ran until the EAS account plan's own limit. A session that expired is replaced by the next run; a run that reuses a live session does not check how much of the cap is left; `stim stop` and `gc --delete` still end a session sooner. EAS rejects a value above the account plan's limit, and that rejection appears as the `eas sim failed` reason. An invalid value in the machine `config.json` refuses with `STIM_BAD_ARG` instead of creating an uncapped session. There is no flag or environment override. Fixes [#3739](https://github.com/appandflow/stim/issues/3739). (`stim`, `@stim-cli/core`) [8e764f689](https://github.com/appandflow/stim/commit/8e764f6893f142c12ab6ba4b15046147cfa6e77d)
- **A `fingerprint-mismatch` refusal from a build worker names the sources that differ and the files the worker rewrote.** Before, a React Native or Expo offload that the worker fingerprinted differently failed with only the two truncated hashes (`the checkout there fingerprints <12>, here <12>`). The reason now also lists, when the worker rewrote synced files, `expo prebuild and pod install there rewrote <files>` and, when the build Mac's stim-server advertises `fingerprint-sources`, `differing sources: <names>` (three names, then `and N more`). The `STIM_OFFLOAD_REFUSED` remedy for a named `--remote-build <machine>` now says to make the named input agree on both Macs (for example by committing the lockfile `pod install` rewrote there) instead of the generic pairing remedy. The client sends each fingerprint source's `id` and `hash` as `fingerprintSources` on `build.start` only to servers that advertise the new feature `fingerprint-sources`. ## Fixes

- **A build worker installs an app's dependencies with the lockfile nearest the app, installs the whole pnpm workspace, and reuses a hoisted install.** The worker finds the first `pnpm-lock.yaml`, `yarn.lock` or `package-lock.json` in the app's directory or above it in the checkout, and runs the install in the directory that holds it: `pnpm install --frozen-lockfile`, `yarn install --frozen-lockfile` or `npm ci`. Before, it looked for a lockfile only at the repository root, so an app with its own lockfile inside a larger repository failed prebuild on the worker, and a pnpm install was filtered to the app and its dependencies (`--filter <package>...`), which missed workspace packages that a Gradle task runs (for example `pnpm run --filter <package>`). The `deps` progress line adds `in <dir>` when the install is not at the checkout root. An install in a subdirectory keeps its own marker (`dependencies-<hash>`), and the worker skips the install when the lockfile, install command and Node major match the marker and `node_modules` exists in the install directory. Before, it required `node_modules` in the app's own directory, so apps whose dependencies are hoisted to the workspace root were reinstalled on every build. The client computes the lockfile hash it sends for dependency ranking from the same nearest lockfile. Fixes [#4070](https://github.com/appandflow/stim/issues/4070), [#4094](https://github.com/appandflow/stim/issues/4094) and [#4091](https://github.com/appandflow/stim/issues/4091). - **An offloaded React Native or Expo build sends the gitignored files its fingerprint reads, so the worker computes the same fingerprint.** Besides the tracked and untracked files git lists, the client now also uploads the gitignored files that the native fingerprint hashes (under fingerprint sources inside the repository, skipping `node_modules` and paths the fingerprint itself ignores) and, when the Expo config is a fingerprint source, the Expo env files that exist (`.env`, `.env.local`, `.env.<mode>`, `.env.<mode>.local`, unless `EXPO_NO_DOTENV` is set). Before, an app whose config reads a gitignored `.env.local` was refused with `fingerprint-mismatch`. These files can hold secrets and now go to the paired worker; nothing under `node_modules` and no build output the fingerprint ignores is sent. Stim's own fingerprint (and so the build cache key) now also ignores Xcode's `*.xcodeproj/xcuserdata` and, for iOS, the `react-native bundle` output `ios/main.jsbundle` and `ios/assets` while a `.gitignore` pattern matches them (even when committed); `stim doctor`'s fingerprint-parity remedy and the `.fingerprintignore` guide text say so. ## Migration notes

- **EAS Simulator sessions now end after 30 minutes by default.** Before 1.24.0 Stim passed no maximum duration, so a session ran until the EAS plan's own limit. For longer sessions, raise the cap up to your plan's limit with `stim settings set remote.easMaxDurationMinutes <minutes> --scope machine`. A run after the cap creates a new session.
- **Update the client Mac and the build or hosting Mac together.** The hosted iOS Expo dev-client fix needs 1.24.0 on both Macs: a 1.24.0 client with an older host, or the reverse, keeps the old random bridge port and the JavaScript still does not load. Offloaded builds already require the same Stim build on both Macs. Update a worker's service with `stim-server service update --release 1.24.0`.
- **Gitignored fingerprint inputs now go to build workers.** An offloaded React Native or Expo build uploads the gitignored files its fingerprint reads, including Expo env files such as `.env.local`, to the paired worker. Pair only workers you trust with those files.
- **Some iOS build-cache keys change once.** Stim's fingerprint now ignores `*.xcodeproj/xcuserdata` and, while a `.gitignore` pattern matches them, `ios/main.jsbundle` and `ios/assets`. A project with those paths misses its existing build-cache entries on the first build after upgrading. Macs still on 1.23.x that share a remote cache compute the old keys for these projects, and Expo CLI builds that use `@stim-cli/expo-build-cache` stop sharing those entries with Stim unless the paths are listed in `.fingerprintignore`.
- **A build worker reinstalls a pnpm repository once.** The worker no longer filters the pnpm install to the app, so a repository installed with the filter under 1.23.x reinstalls on its first 1.24.0 build.
- **Hosted log records written before 1.24.0 drop out of `logs --errors` and the `status` error counts.** This includes hosted Android crash lines, which were never stamped `native_crash`. The records are not rewritten and remain under `--source device` and `--source all`.
