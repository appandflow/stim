# 1.34.0

Stim Desktop and the Stim phone app ship through their own workflows; this release covers the thirteen npm packages (`@stim-cli/core`, `@stim-cli/cache`, `@stim-cli/cache-s3`, `@stim-cli/agent-driver`, `@stim-cli/agent-driver-agent-device`, `@stim-cli/metro`, `@stim-cli/expo-build-cache`, `stim`, `@stim-cli/ci`, `@stim-cli/transport`, `@stim-cli/transport-tailscale`, `@stim-cli/transport-local` and `@stim-cli/server`). No package publishes for the first time in this release. The release was frozen at [3bb4a69a5](https://github.com/appandflow/stim/commit/3bb4a69a5efa355a040c1a8ef0eca23765b2c133) ([#4546](https://github.com/appandflow/stim/pull/4546)). Every commit since v1.33.0 has an entry below. [#4547](https://github.com/appandflow/stim/pull/4547), which clears a worker's `Pods/Local Podspecs` before `pod install` ([#4545](https://github.com/appandflow/stim/issues/4545)), had not merged at the freeze and is not in this release: a worker still fails `pod install` with `hermes-engine ... differs from the version stored in Pods/Local Podspecs` after a job on another React Native version. Stim Desktop is unchanged since desktop-v0.2.13, so there is no Stim Desktop release for this version.

## New

- **An offloaded iOS build from a client without Xcode reuses the worker's app after `pod install`.** Since 1.33.0, a client without Xcode whose committed `Podfile.lock` is stale offloads every iOS build: its lookup uses the fingerprint before `pod install`, which never matches the one the worker stores under, so the worker ran `pod install` and then xcodebuild on every run, even when stim-server already held an app built under the post-`pod install` fingerprint. The worker now looks that fingerprint up in stim-server's retained artifacts once, after `pod install` and before compiling, as a local build does after a mutating `pod install`. On a hit it unpacks the retained app, reports `buildMs` 0 and skips xcodebuild, and the client prints `reused artifact from <mac>` instead of `built on <mac>`, counted as a remote cache hit. A miss or any error reading the cache compiles as before, and the app is still stored only under the post-`pod install` fingerprint. `pod install` still runs on the worker on every such run, since only the worker can compute that fingerprint. The worker reuses only when the client's cache reads allow it, so `stim ios --no-build-cache` still compiles; Release configurations never reuse. The client sends the new `build.start` field `reuseArtifact` only with `podsOnWorker`, and only to a server that advertises the new hello feature `build-reuse-artifact`. The artifact store the server writes moves into `stim` as the export `stim/build-artifact-cache`, so the worker reads it without a second implementation, and `@stim-cli/server` no longer depends on `@stim-cli/cache` directly. `stim guide settings`, the `@stim-cli/server` README and the remote machines website page describe it. Fixes [#4536](https://github.com/appandflow/stim/issues/4536). (`stim`, `@stim-cli/server`, `@stim-cli/core`) [6e49db16e](https://github.com/appandflow/stim/commit/6e49db16ef670ea84ee725887907be2077755e02)

## Fixes

- **Hosted iOS from a Linux client reaches its own Metro in an Expo dev-client app configured by `app.config.ts`.** `stim ios --remote <mac>` from a client without `plutil`, such as Linux, launched the app on the hosted simulator, but the dev client never loaded a bundle and Stim reported `no bundle request reached this workspace's Metro`. Stim read the built app's URL schemes only with `plutil`; without it, the dev-client scheme fell back to `app.json`, which an `app.config.ts` project lacks, so the worker's Metro bridge opened without the client's Metro port, bound a random port and launched with a location expo-dev-launcher ignores. When `plutil` fails, Stim now reads the app's `Info.plist` in process, binary (`bplist00`, as Xcode writes it) or XML. macOS still uses `plutil`. A malformed or unsupported plist still falls back to `app.json`. Fixes [#4541](https://github.com/appandflow/stim/issues/4541). (`stim`) [b7846eb21](https://github.com/appandflow/stim/commit/b7846eb2105f76fc592308a13115f1154add6422)
- **Hosted iOS from a Linux client installs an app whose project declares no bundle identifier.** A client without `plutil` and `defaults` found no bundle identifier in the app it fetched from the worker, so when the project declared none either (react-native-test-app projects, or an Expo app without `ios.bundleIdentifier`), `stim ios --remote <mac>` failed with `The built app has no bundle identifier.` and `STIM_INSTALL_FAILED`. Stim now reads `CFBundleIdentifier` from the app's binary or XML `Info.plist` in process after `plutil` and `defaults` fail. macOS behavior is unchanged. Fixes [#4544](https://github.com/appandflow/stim/issues/4544). (`stim`) [3bb4a69a5](https://github.com/appandflow/stim/commit/3bb4a69a5efa355a040c1a8ef0eca23765b2c133)

## Migration notes

- **Update the worker for the reuse after `pod install`.** [#4539](https://github.com/appandflow/stim/pull/4539) needs 1.34.0 on both the client and the worker: run `stim-server service update --release 1.34.0` on each worker Mac, or install `@stim-cli/server` 1.34.0. A 1.33.0 worker does not advertise `build-reuse-artifact`, so a 1.34.0 client does not send `reuseArtifact` and the worker compiles as before; a 1.33.0 client never sends it. The worker-side `Pods/Local Podspecs` clear ([#4547](https://github.com/appandflow/stim/pull/4547)) is not in 1.34.0, so updating the worker does not fix a `pod install` that fails after a job on another React Native version.
- **The Linux-client fixes are client-side.** The dev-client scheme ([#4543](https://github.com/appandflow/stim/pull/4543)) and the bundle identifier ([#4546](https://github.com/appandflow/stim/pull/4546)) need only `stim` 1.34.0 on the client; the worker can stay on 1.33.0. A workspace whose hosted Metro bridge was opened by an older client without the client's Metro port needs one `stim stop` before the next `stim ios --remote`: the worker refuses to change a live bridge's client port.
- **Build offload is unaffected.** `STIM_BUILD_COMPAT` stays 2, so 1.31.0 through 1.34.0 machines still offload builds to each other.
- **New fields, no new state files.** The `build.start` request gains the optional `reuseArtifact`, the `build.start` job outcome the optional `reused: true`, and `hello` the feature `build-reuse-artifact`. Like `podsOnWorker`, `reuseArtifact` is missing from the published `protocol.schema.json` ([#4538](https://github.com/appandflow/stim/issues/4538)); the server accepts it. No setting changes.
