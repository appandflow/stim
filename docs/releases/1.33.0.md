# 1.33.0

Stim Desktop and the Stim phone app ship through their own workflows; this release covers the thirteen npm packages (`@stim-cli/core`, `@stim-cli/cache`, `@stim-cli/cache-s3`, `@stim-cli/agent-driver`, `@stim-cli/agent-driver-agent-device`, `@stim-cli/metro`, `@stim-cli/expo-build-cache`, `stim`, `@stim-cli/ci`, `@stim-cli/transport`, `@stim-cli/transport-tailscale`, `@stim-cli/transport-local` and `@stim-cli/server`). No package publishes for the first time in this release. The release was frozen at [5806b8fea](https://github.com/appandflow/stim/commit/5806b8fea45ee3b7f08133832271690000da7f19) ([#4535](https://github.com/appandflow/stim/pull/4535)). Four commits since v1.32.0 change only Stim Desktop and the website, none of the npm packages, and have no entry below: [#4523](https://github.com/appandflow/stim/pull/4523) (on a paired machine whose server granted this Mac `control`, Stim Desktop runs Reload App and Stop and opens and controls its iOS and Android device screens), [#4526](https://github.com/appandflow/stim/pull/4526) (a workspace outside its project is titled by its folder), [#3189](https://github.com/appandflow/stim/pull/3189) (the Machines screen is split into Overview, Builds and Storage tabs) and [#4533](https://github.com/appandflow/stim/pull/4533) (a dismissed unfinished tutorial stays closed at launch). The Stim Desktop release built from this commit carries them.

## New

- **Stim installs a missing Android system image, locally and on the hosting Mac.** When no installed system image matched, `stim android` stopped and asked a person to run `sdkmanager`, and `stim android --remote <mac>` refused with `STIM_HOSTING_REFUSED: <mac>: No compatible installed Android image.`, which nothing on the client could fix. A new setting, `android.installImages` (`auto` by default, or `never`), lets Stim install it. When no installed image matches, Stim picks the image `--system-image` or `android.systemImage` names, else `system-images;android-36;google_apis;<host ABI>`, and runs the SDK's own `cmdline-tools/latest/bin/sdkmanager --sdk_root=<sdk> --install <package>` before it creates the owned AVD, printing `image  installing <package>`. Stim never accepts a license: it refuses before sdkmanager runs when `licenses/android-sdk-license` is missing, answers `n` to any prompt sdkmanager still shows (the arm64 image also needs `android-sdk-arm-dbt-license`), and both refusals name `sdkmanager --licenses`. It installs only host-ABI images and needs `cmdline-tools/latest` and 8 GB free on the SDK volume; otherwise it refuses before any download, naming the command-line tools when they are missing and the exact `sdkmanager --install` line for a wrong-ABI image or any missing image under `never`; the error codes are unchanged (`STIM_BAD_ARG` for a named image, `STIM_NO_DEVICE` otherwise). One install runs per SDK root and Stim home, under an ownership claim at `$STIM_HOME/android-sdk-installs/<hash>` with sdkmanager as its child; a second run waits and then finds the image. A run that keeps an emulator that already booted never installs. Two Stim homes sharing one SDK are not serialized against each other, an install that Android Studio runs at the same moment is not detected, and the install runs before the device capacity check, so `--no-wait` with `concurrency.maxDevices` full downloads the image and then refuses. After an install, the foldable profile checks run again against the installed image. The image directory is recorded under a new `systemImages` key in `created-devices.json`, and `gc --json` marks it `stimInstalled`; `gc` still only prints the `sdkmanager --uninstall` line. `stim doctor` reports a missing image as the note `android-system-image`, and `doctor --fix` installs it. `--plan` keys on the ABI of the image a run would install. For a hosted run, the hosting Mac decides with its own machine `android.installImages`, checks licenses, tools and disk when it offers, and installs the image in its own Stim home before it prepares the device, within 30 minutes; the client prints `image  installing <package> on <mac>` and waits that long. A failed install stops the session with the refusal as its notice. `stim guide lifecycle`, `settings`, `errors` and `agent`, the `@stim-cli/server` README and the commands, owned devices, remote machines, requirements and settings website pages describe it. Fixes [#4520](https://github.com/appandflow/stim/issues/4520). (`stim`, `@stim-cli/server`, `@stim-cli/core`) [ee9c0e86c](https://github.com/appandflow/stim/commit/ee9c0e86ce4e047099853297f99f7d3c34024790)
- **Android builds offload from a client without a JDK or Android SDK.** A client with no JDK, such as a Linux VM, refused every remote machine for an Android build (`Remote machine <mac> runs another JDK major version`, "JDK 17 there, none here"), so the build fell back to this machine, where it cannot work. Such a client now builds on the worker's default JDK, whatever its major version, and refuses only a worker that has none (`no JDK there`, with the JDK 17 install command for the worker's OS). `stim doctor` and the `offload:` line of `stim android` show the note `Remote machine <mac> builds Android with its own JDK` instead of a warning. Clients with a JDK keep the strict major-version match. With `remote.build: auto` a client that is not busy still builds here, as an iOS client without Xcode does; name the machine with `--remote-build <mac>`, `STIM_REMOTE_BUILD` or `remote.build`, or use `remote`/`remote-only`. `stim guide settings` and the remote machines and requirements website pages describe it. Fixes [#4521](https://github.com/appandflow/stim/issues/4521). (`stim`) [df9430f03](https://github.com/appandflow/stim/commit/df9430f03d5bf5df681736c720e02abfbfbc61c4)
- **More agent-device commands on hosted iOS simulators and Android emulators, with flags that fail closed.** The hosting Mac's relay allowed 25 of agent-device 0.21.31's 75 commands and refused the rest with one generic sentence. Its policy now lists each allowed command and, for every flag, whether it is allowed. Newly allowed are commands that act only on the hosted device, among them `gesture`, `fold`, `keyboard`, `apps`, `capabilities`, `events`, `app-switcher`, `action-button`, `hardware-button`, `telephony`, `trigger-app-event`, `react-native`, `network`, `artifacts`, `settings`, `push` (an app id and an inline JSON object only) and `perf` (`frames` and `memory sample` only). Every other command is refused with its own reason, for example `audio` because it samples the hosting Mac, and `uninstall` and `clipboard` stay refused. `settings permission` refuses the host permissions `accessibility`, `screen-recording` and `input-monitoring`. A flag or request key the policy does not list is now refused, including inside `batch`, instead of reaching the daemon unless a deny-list named it. `open --metro-host`, `--metro-port`, `--bundle-url` and `--launch-url` are refused instead of being dropped silently: the hosted Metro endpoint comes from Stim, not from agent-device hints. The hosting Mac needs agent-device 0.21.30 or later for iOS and Android, and now checks it for iOS too, so an older one reports `driver: none` instead of a dead proxy. `stim guide lifecycle` and `settings`, the `@stim-cli/server` README and the commands, owned devices, remote machines and settings website pages list the allowed and refused commands. Fixes [#4516](https://github.com/appandflow/stim/issues/4516). ## Fixes

- **An offloaded React Native iOS build from a client without Xcode survives a stale `Podfile.lock`.** A client without Xcode leaves `pod install` to the worker Mac. When the committed `Podfile.lock` was stale, the worker's `pod install` rewrote it, the worker's fingerprint no longer matched the client's, and the worker refused with `fingerprint-mismatch`, which the client could not fix without a Mac. Such a client now sends `podsOnWorker` with the build. The worker then accepts a different fingerprint only when the fingerprint sources the client sent differ from its own after `pod install`, and only inside the iOS project directory; any other difference still refuses with the existing message. It builds and reports the fingerprint it built under. The client accepts that fingerprint (40 to 128 lowercase hex characters) and stores the app, `lastBuild` and the upload only under it, printing `fingerprint <pre> -> <post> (as <mac> built it)`; the lookup and the single-flight lock stay on the pre-mutation key. The worker keeps its peer artifact only under the fingerprint it built under. Clients with Xcode and every other job keep the strict comparison. Later runs from a client whose committed lock stays stale do not hit the cache, because its lookups use the pre-mutation key; each run reruns `pod install` and an incremental build on the worker. `stim guide settings` and the remote machines website page describe it. Fixes [#4469](https://github.com/appandflow/stim/issues/4469). (`stim`, `@stim-cli/server`, `@stim-cli/core`) [5806b8fea](https://github.com/appandflow/stim/commit/5806b8fea45ee3b7f08133832271690000da7f19)
- **Hosted `agent-device record` works on a worker whose Stim home is on an external volume.** On janics-mac-mini, whose `~/.stim` lives on an external SSD, `record start` failed with `simctl recordVideo exited with code 1`: the simulator's `SimRenderServer` writes the file, and macOS denies it the Removable Volumes permission. The relay now records into `<os tmpdir>/stim-server-recordings-<hash>/<random>/` with mode 0700, where `<hash>` is derived from the session's agent-device state directory, so driver stop, teardown and daemon start still find and delete it. It refuses to record (500, logged) unless that parent is a real directory owned by the server's user with no group or other access. `stim gc --delete` already sweeps `stim-server-` leftovers in the temp directory after 24 hours. `stim guide lifecycle`, the `@stim-cli/server` README and the owned devices and remote machines website pages say where the host writes recordings. Fixes [#4529](https://github.com/appandflow/stim/issues/4529). (`@stim-cli/agent-driver-agent-device`, `@stim-cli/server`, `stim`) [685710464](https://github.com/appandflow/stim/commit/6857104643dd92be1cfb3634b62ed238339c3e69)
- **A workspace whose folder was deleted is reported, and `stim worktree remove` drops it.** A workspace removed outside Stim stayed `ready` in `stim status` and in Stim Desktop's Live filter, and `stim worktree remove <path>` refused it with `No such worktree`. `stim status` now sets `pathMissing: true` on an environment whose path is gone from a mounted volume, never reports it `warming` or `ready`, and prints `[folder missing]` with a remedy line; an unreadable folder is not reported. `stim worktree remove <path>` on such a path reclaims the record of that path and of projects registered under it through the existing reclaim flow, including owned devices through centralized teardown. A path on an unmounted volume is refused with the volume named and its record kept, and the automatic sweep is unchanged. Stim Desktop reads `pathMissing` and shows `Folder missing`. `stim guide` (status facts, lifecycle, cleanup) and the commands and worktrees website pages describe it. Fixes [#4518](https://github.com/appandflow/stim/issues/4518). (`stim`, `@stim-cli/core`) [8d047812f](https://github.com/appandflow/stim/commit/8d047812f8135e283d51a66cb88422d0f49321a0)

## Migration notes

- **`android.installImages` defaults to `auto`.** From 1.33.0, `stim android` downloads a missing host-ABI system image with the SDK's sdkmanager when its licenses are accepted, cmdline-tools are installed and 8 GB are free. It never accepts a license. To keep the old refusal, run `stim settings set android.installImages never` (at `--scope machine` for the whole machine). For a hosted run the hosting Mac's machine value decides and the client's value is not used, so a worker owner who wants no downloads sets `never` at machine scope there. An older `stim` that writes `created-devices.json` drops the new `systemImages` key, which only makes an image read as not installed by Stim.
- **Hosted agent control needs agent-device 0.21.30 or later on both machines**, for iOS and Android. The floor was 0.21.20 for iOS and 0.21.22 for Android, so a hosting Mac on 0.21.20 through 0.21.29 that worked with 1.32.0 reports agent control as `driver: none` after the update to 1.33.0; `stim doctor` names the new floor. Update with `npm install --global --prefix "$HOME/.local" agent-device`.
- **Some agent-device requests a 1.32.0 host forwarded are now refused.** A flag or request key the hosted policy does not list for that command is refused with rule `request`, and `open --metro-host`, `--metro-port`, `--bundle-url` and `--launch-url` are refused with rule `host-path` where a 1.32.0 host dropped them silently. Scripts that pass those hints to a hosted device must drop them; Stim sets up the hosted Metro endpoint itself.
- **Update the worker for the hosting fixes.** Run `stim-server service update --release 1.33.0` on each hosting Mac, or install `@stim-cli/server` 1.33.0:
  - Hosted recording into the temp directory ([#4530](https://github.com/appandflow/stim/pull/4530)) and the hosted command policy ([#4524](https://github.com/appandflow/stim/pull/4524)) run in stim-server; the client needs no update for them.
  - The hosted image install ([#4528](https://github.com/appandflow/stim/pull/4528)) needs a 1.33.0 worker. A 1.32.0 worker still declines with `No compatible installed Android image.` An older client against a 1.33.0 worker gets the install, but its 5-minute preparing wait can run out first; the session survives, and a 1.33.0 client's next run attaches to it with the longer wait.
  - The pods refingerprint ([#4535](https://github.com/appandflow/stim/pull/4535)) needs 1.33.0 on both the client and the worker. An older worker ignores `podsOnWorker` and refuses as before, and an older client never sends it.
- **Client-only changes.** The JDK-less Android offload ([#4522](https://github.com/appandflow/stim/pull/4522)) and the deleted-folder report and removal ([#4525](https://github.com/appandflow/stim/pull/4525)) need only `stim` 1.33.0 on the client.
- **Build offload is unaffected.** `STIM_BUILD_COMPAT` stays 2, so 1.31.0, 1.32.0 and 1.33.0 machines still offload builds to each other.
- **New fields, no new state files.** `stim status --json` gains the optional `pathMissing` on an environment, `created-devices.json` the `systemImages` key, the `build.start` request the optional `podsOnWorker` (missing from the published `protocol.schema.json`, [#4538](https://github.com/appandflow/stim/issues/4538); the server accepts it), and the hosted Android offer the optional `installImage`. The setting `android.installImages` is new.
