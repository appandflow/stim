# 2.0.0-rc.7

Install `stim@2.0.0-rc.7` to try the seventh Stim 2.0 release candidate. The optional S3 cache provider is available as `@stim-cli/cache-s3@2.0.0-rc.7`.

## New

- **`stim worktree list [--all] [--json]` lists linked worktrees with their real size and cleanup's verdict.** Each line shows the path, branch, idle days, real and apparent size, the state in gc's words (`kept: <reason>` or `removed by cleanup: <reason>`), and the marks `old` (idle 30 days or more) and `large` (1 GiB real or more). Lines are sorted by real size, largest first, with unknown sizes last, and a summary gives the count, the real total, what cleanup removes by itself and what kept worktrees hold, split by keep reason. Real size is what deleting the worktree frees: a worktree warmed from the main checkout shares most of its `node_modules` blocks with it, so it can be far smaller than its apparent size. When the volume cannot count shared bytes, or a walk could not read every file, the real size is unknown and is left out of the totals. The default lists the current repository and runs the same worktree check as `stim gc --dry-run`, without a fetch or `gh`. `--all` lists every repository from the verdicts automatic maintenance saved, marks a worktree with no saved verdict `not checked`, says how old each repository's verdicts are, and adds a grand total; with `daemon.mode` off, a line on stderr says the saved verdicts are not refreshed. A worktree's size is composed of its `node_modules` and `ios/Pods`, reused under the dependency tree rule below, and the rest of the worktree, walked again when its measure is over an hour old; a worktree with a project-local `.pnpm-store`, or whose `node_modules`, `ios` or `ios/Pods` is not a plain directory, is walked whole. The walks share one 2 minute budget for the whole command; a worktree the budget leaves unwalked keeps its older measure or prints `not measured`. A worktree that cleanup would remove is listed as kept, reason `removal-off`, naming the setting, when `maintenance.removeFinishedWorktrees` is off, or for an idle removal when `maintenance.removeIdleWorktrees` is off or `maintenance.olderThanDays` is 0. The listing goes to stdout, progress to stderr, and `--json` prints one payload with `daemonMode`, and `checkedAt` and `oldestCheckedAt` per repository. The command deletes nothing, takes no admission and starts no stimd. [f42c02e309](https://github.com/appandflow/stim/commit/f42c02e309fe0867fd278a79fa101b3a5be7f67d) [e5506ea31d](https://github.com/appandflow/stim/commit/e5506ea31dd988c3b85db4dfe774c29685225ba5) [ac861e1564](https://github.com/appandflow/stim/commit/ac861e1564c2456c7961a1600aceaef96e888b30)
- **`stim doctor` in a git repository adds a `linked-worktrees` note.** Its title gives the repository's linked worktree count, their real size and what kept worktrees hold, or, with none here, the machine's count and real size. The note carries the `stim worktree list` summary line, up to three old or large kept worktrees with their reason, real size and idle days, how old the saved verdicts and sizes are, and one sentence over this repository and every repository maintenance has checked on this machine. It also says when automatic maintenance is off or only reports, or `maintenance.removeFinishedWorktrees` is off, so the saved verdicts are not refreshed, and points at `stim worktree list` and `stim worktree list --all`. Doctor reads only saved verdicts and sizes: it never measures or checks a worktree. Without a check, the note says the maintenance worktree check has not run for this repository. There is no note outside a git repository, or when neither this repository nor any repository on the machine has linked worktrees. `--fix` does nothing with it. [e5506ea31d](https://github.com/appandflow/stim/commit/e5506ea31dd988c3b85db4dfe774c29685225ba5)
- **Sizes are measured by the bundled `real-size` binary.** Stim measures what deleting a folder would free with the prebuilt binary of `real-size` 0.2.0, a new dependency of `stim`, instead of a helper it compiled with the Xcode Command Line Tools on first use. The measure is clone-aware: on APFS, and on Linux ext2/3/4, tmpfs, btrfs and XFS, blocks shared with a clone or a hard link do not count as private. macOS numbers are unchanged, no longer need the Command Line Tools, and the walk lists directories on up to four threads. Linux btrfs and XFS now report private bytes where Stim reported them unknown. A tree with an entry the walk cannot read, or with a volume mounted inside it that cannot report private sizes, now reports both sizes as a lower bound ("at least"); on macOS such a tree reported `du` bytes with private bytes unknown. On macOS, a measured path that is not on APFS, including an empty folder, reports private bytes unknown. Windows still has no private size. A `stim-privsize-<hash>` helper left in `$STIM_HOME/helpers` by an earlier Stim stays there. [67933f5f9e](https://github.com/appandflow/stim/commit/67933f5f9ed49b783496b2fd3c0aed631f59133b) [066590e6e5](https://github.com/appandflow/stim/commit/066590e6e51eb4e6a3665b7b4bd1c31d5db2213d) [4b6a0fddde](https://github.com/appandflow/stim/commit/4b6a0fddde18c245f376c0952beadbbb2196460e)
- **A dependency tree size is reused until its clone group changes, for up to a day.** A `node_modules` or `ios/Pods` size whose install signature is unchanged is reused for 6 hours, as before, then up to 1 day while its clone group is unchanged, and walked again after a day. The clone group is the same path in every checkout of the repository: an install, reinstall or removal of that tree in any of them, or a new linked worktree, changes it. This applies to the daemon's dependency scan and to `stim status`, `stim gc` and `stim worktree list`. [6b0c77bb6c](https://github.com/appandflow/stim/commit/6b0c77bb6cee5166f8ffc075a713a2a9d3424811)
- **The `stim status` checkout size walk leaves out dependency trees.** It leaves out `node_modules` and `ios/Pods` at the checkout root and at every Stim workspace path inside it, and adds their sizes from the dependency rule, so a periodic status walk no longer reads an app's Pods again. When one of those trees is unknown or was reinstalled, the checkout size falls back to the whole-checkout measure or is unknown. [845eea7a64](https://github.com/appandflow/stim/commit/845eea7a6461c267f65518c1775f903eb07d1c18)
- **Cache and Cargo `target/` sizes are reused under their caps.** The daemon's size scan reuses the measured sizes of the build, Metro and Swift compilation caches while every folder of a category has a complete measure under 6 hours old and their total is at or under the cap; otherwise it walks every folder of that category again. A Cargo `target/` size is reused for 6 hours only while it is complete and at or under the cap. ccache and caches without a cap are reused for 6 hours, and `stim gc` reuses its sizes of other Stim homes and private machine-cache folders for 1 hour. So a cache that grew past its cap can stay there for up to 6 hours before it is trimmed, and an acting `stim gc` plans from the same sizes. [38853c0a71](https://github.com/appandflow/stim/commit/38853c0a715db2fab7c4b0846e6534352dcb8200)

## Fixes

- `stim worktree remove` run right after `stim stop` waits up to 60 seconds, shared across the workspaces it removes, for a background pass (a daemon stage, gc, fingerprint evaluation or `doctor --fix`) that holds the workspace's native-run lock, printing a `lock  waiting for ...` line on stderr, instead of keeping the workspace. A `stim ios`, `android`, `stop` or `share` run, or a holder that records no details, still makes it refuse at once. The refusal now names the holder, for example ``kept because `stim ios` (pid 456, running for 3m10s) holds its native-run.lock``, and the wait lines of `ios`, `android` and `stop` name a background pass by its purpose, such as `Stim's idle stage`, instead of `another Stim run`. gc's automatic removal does not wait. [6f98cfd830](https://github.com/appandflow/stim/commit/6f98cfd830d0bf4b96025fdbb759039cfa9b7742)
- The engine store's weekly npm cache trim no longer leaves index records whose content it removed, which after a week made every `stim engine use` and `stim engine update` fail with `ENOENT` under `.npm-cache/_cacache`. Once any file there that no offload job keeps is a week old, every such file goes. An engine install or an offload job install that still meets a missing cache file clears the engine's `.npm-cache` and runs once more; a second failure adds the `rm -rf` command for that cache. On a machine already stuck, run `rm -rf ~/.stim/engine/.npm-cache` (or `$STIM_ENGINE_ROOT/.npm-cache`) once, then the same command again, because its engine predates the fix. [33ec7da39d](https://github.com/appandflow/stim/commit/33ec7da39db1bc1552860b28483014ceb2a41d5e)
- When Stim Desktop asks for net thread options that differ from the running ones (for example after turning on Allow connections) while offloaded jobs, hosted device sessions or workspace actions are under way, stimd keeps the running listener instead of restarting it and ending that work. It applies the new options once that work ends. Every hosted device session counts, an idle one too, so an Allow connections change waits until the session stops. [7f59679d7c](https://github.com/appandflow/stim/commit/7f59679d7c8c34f9f13b4673ac77d73f95a65038)
- Stim Desktop, in its next release: Rotate Left and Rotate Right on a local simulator tile turn the picture and touch mapping with the simulator while a portrait-only app is in front. A two-screen simulator still follows the app. A turn from an earlier boot is forgotten, since a simulator boots upright. A turn made from a share or the phone app is still not seen by the Desktop tile. [4d98850f7a](https://github.com/appandflow/stim/commit/4d98850f7a5e5fcd44b62496bc10c3267eca1713)

## Migration notes

- **A machine whose engine npm cache is already broken stays broken until it is cleared once.** Run `rm -rf ~/.stim/engine/.npm-cache` (or `$STIM_ENGINE_ROOT/.npm-cache`), then `stim engine update` or `stim engine use <version>` again. [33ec7da39d](https://github.com/appandflow/stim/commit/33ec7da39db1bc1552860b28483014ceb2a41d5e)

For upgrade steps, see the [Stim 2.0 upgrade guide](https://stim.appandflow.com/docs/migrate-to-2).
