# 2.0.0-rc.6

Install `stim@2.0.0-rc.6` to try the sixth Stim 2.0 release candidate. The optional S3 cache provider is available as `@stim-cli/cache-s3@2.0.0-rc.6`.

## New

- **Hosted simulators and emulators refuse known harmful commands instead of allowing a fixed list.** Any agent-device command and flag now passes on a hosted iOS simulator or Android emulator except a refused list, so `audit` and `shake`, which were refused on every host, now work where the host's agent-device has them, and a command or flag a newer agent-device adds passes without a Stim update. Still refused, each with its reason: `install`, `reinstall`, `install-from-source` and `uninstall`, `boot`, `shutdown` and `close --shutdown`, `logs`, `trace`, `audio`, `doctor`, `prepare`, `replay` and `test`, `clipboard`, `hover`, `viewport`, `tv-remote` and agent-device's client-side commands, matched case-insensitively. Refused inputs are host paths, launch inputs (`--launch-args`, `--launch-url`, `--bundle-url` and the like), a client-chosen Metro address, `--save-script`, device or OS selection, recording repair flags and fullscreen screenshots; a refusal names the flag. `open` and `close` take app ids only, `perf` allows only frames and memory sample, `push` takes an inline JSON payload, and screenshot and record use remote destinations, as before. The device policy given to the agent-device daemon no longer names commands. Both machines still need agent-device 0.21.30 or later. [89b871c626](https://github.com/appandflow/stim/commit/89b871c626ad8fdb43348c4e9fb9ca2d00e187f8)
- **Stim's churn folders end in `.noindex`, so macOS Spotlight skips them.** The folders are `metro-cache.noindex`, `compilation-cache.noindex` and `ccache.noindex` in the Stim home, and `agent-device.noindex` in each workspace, on every platform. An upgraded home keeps using its old folders until stimd renames each one in place at the start of a maintenance pass, with `daemon.mode` set to `on` (never in `report`), once no build, dev server or agent-device daemon holds it. `stim start`, the boot hook and `stim agent-device` also rename their own workspace's agent-device folder. Nothing is copied, merged or deleted: an old folder left beside its new name stays, and gc measures and trims it under its category. After the move, a link at `compilation-cache` (a junction on Windows) points to the new folder, so builds outside Stim that share the cache stay warm. A symlinked folder, and a path set with `caches.metroCache`, `STIM_METRO_CACHE` or `server.workerRoot`, never moves; set `server.workerRoot` to a `*.noindex` path to keep worker checkouts out of Spotlight. Removing a workspace archives its agent-device sessions from both folder names into the unchanged `archive/<id>/agent-device/sessions`, renaming a session whose name is already taken instead of overwriting it, and refuses the archive when a state or sessions folder is a link. [9cc203f737](https://github.com/appandflow/stim/commit/9cc203f7376a7ff7d1e2dc43f69947320b098ae1)
- A workspace service can declare `envFile`, a path relative to the workspace that must stay inside the checkout, like `cwd`. Stim reads it each time it runs one of the service's commands (start, ready, stop and teardown) or starts its supervised process, so an edit after the start reaches the next stop or teardown. Only the path is recorded: the file's values are not written to workspace state, printed by `stim services env` or shown in a run-by-hand remedy, which says `with the variables of <envFile>` instead. A declared `env`, the port variables and `idEnv` win over a same-named entry in the file. A missing or unreadable file fails that command with `could not read envFile <path>: <code>`. The orphan teardown, which runs after the worktree folder is gone, runs without the file. [b75576105b](https://github.com/appandflow/stim/commit/b75576105b7a369c31590e4edaf7a68718deca44)
- A paired device with view access can rename its own record on a machine with the new `device.rename` request. It uses the name rule of `stim pairings rename`, can rename only the device's own record (any other id is refused with `forbidden`), and writes every rename and refusal to the action log. An older machine answers `unknown-method`. The Stim phone app, in its next release, adds a Rename This Phone button to each connected machine on the Machines screen; on a machine whose Stim predates the request it explains how to rename the phone there with `stim pairings rename <id> <name>`. [d844c89926](https://github.com/appandflow/stim/commit/d844c8992606169eb9f587604cdc6aa8ab03061f) [8a4f098f3d](https://github.com/appandflow/stim/commit/8a4f098f3d982e817f0f7fbb67d4678c15b70f01)
- `android.avdConfig` and `android.avdConfigFile` accept `fastboot.forceColdBoot` (`yes` or `no`), so a project whose tests fail after a Quick Boot snapshot can ask for cold boots. Like the other keys, it applies only to AVDs Stim creates after the change, and AVDs with it form their own pool. The other `fastboot.*` keys stay refused. [5d80a88705](https://github.com/appandflow/stim/commit/5d80a88705b320ba3427601a69b225fc604885f8)
- When a client removes a worktree (`stim worktree remove`, gc, automatic maintenance or a reclaim), it asks each build worker that built that checkout to drop the checkout's build area under `server.workerRoot`, instead of leaving it until `server.workerAreaMaxAgeDays`. The worker keeps an area that a live job, a kept bundle, a pin, a running Gradle daemon, a claim or a device ledger still holds. The client records the workers it offloads to from this release on, asks only when the checkout is gone from a disk that is still mounted, and waits at most 5 seconds; the removal never fails because of it. `stim worktree remove` prints one stderr line per area dropped or kept. A worker on an earlier Stim refuses the request and keeps ageing its areas out. [2e2d010338](https://github.com/appandflow/stim/commit/2e2d0103388428af49174aea7dbdb2c136aae7cb)
- The `daemon_step` record of pressure ladder rung 1 in `daemon.ndjson` splits its time into parts: `marksMs`, `queueMs`, `authorizeMs`, `measureMs`, `clearMs`, `refreshDiscoverMs` and `refreshReadMs`, with `targets`, and `slowestTarget` and `slowestRoot` with their times. A part that never ran has no field. [5084b27bb9](https://github.com/appandflow/stim/commit/5084b27bb91cea245f10886632b0f7c5168ce6c1)

## Removed (breaking)

- **A service unit that names node is no longer moved onto the engine launcher when its server boots.** A LaunchAgent or systemd unit installed before the engine store keeps running the build it names, and does not follow `stim engine update` or `stim remote update`, until `stim service install` (or `stim setup`) runs once on that machine. On Linux the one automatic idle restart that applied the move is gone too. Once the engine is installed, `stim doctor` (as `server-service-stale`), `stim service status` and `stim setup` report such a unit as stale with the install command, now also for a systemd unit that names node. [a72e437c0a](https://github.com/appandflow/stim/commit/a72e437c0aa8bcbfa9b91659f05f9dc95244e768)
- **A running Stim 1.40 stim-daemon is no longer stopped and taken over.** While a 1.40 to 1.42 stim-daemon holds the home's daemon claim, every command that starts stimd (`stim start`, `ios`, `android`, `web`, `macos`, `revive` and an acting `stim gc`) refuses before it starts anything, with `STIM_DAEMON_UNAVAILABLE`, the daemon's pid and its stop command (`kill <pid>`, or `taskkill /PID <pid> /F` on Windows). A stimd started by Stim Desktop fails the same way. `stim status` and `stim doctor` print the stop command instead of saying the next command stops the daemon. Stop the old daemon before the first 2.0 command, as the upgrade guide says. [27feac0daf](https://github.com/appandflow/stim/commit/27feac0dafcf7f0548e73d69eea5fc7e3dcfcc92)

## Fixes

- `stim service install --helper` installs or updates Stim Host to the pinned, verified release before it registers the helper, instead of failing with `usage: stim-host run` on a Mac with no Stim Host or one older than 0.2.0. It can therefore download, and it does not install the server service. When the download or check fails, it reports that and registers nothing. `stim service status` ends its `Stim Host too old` line with that command. [cd81882a6d](https://github.com/appandflow/stim/commit/cd81882a6dff04d935f44638de8697170bf34b91)
- `stim engine use` with the build that is already current, while a build or hosted session holds a stimd claim, applies the pin and channel and leaves no stage. It used to leave a `staged` entry naming the running build that never cleared. A machine that already has one clears it on its next `stim engine use` or `stim engine update`. [aff24d59fb](https://github.com/appandflow/stim/commit/aff24d59fb0d70f8aa981dd3624ad15ff2c7c2e5)
- `stim engine uninstall` run through an installed `stim` keeps the engine build it runs from, instead of deleting it and exiting 1 with `ERR_MODULE_NOT_FOUND` after the uninstall had completed. Its last line names what the root keeps and says to delete it once no `stim` runs from there. [f0dfb6d528](https://github.com/appandflow/stim/commit/f0dfb6d528368e1620efc48270934a3d2d543507)
- A command whose bounded filesystem read never answered (a dead network mount, for example) now exits with its own status once it finishes, on macOS and Linux with Node 22.15.0 or later. It used to stay running until the read answered, and the exits `stim gc` and `stim doctor` attempted blocked the same way. On Windows and on Node before 22.15 it still waits for the read to answer, as before. [a7107024fc](https://github.com/appandflow/stim/commit/a7107024fc6712f81db496386037febc121a9cb1)
- A foreground `stim serve` that runs stimd in its own process starts libuv with 16 threads, as a stimd started by Stim already did, on Node 24 and on Node 22 from a version after 22.14 (22.20 and later are confirmed). On Node 22.12 and 22.14 it keeps 4 threads. Unless you set `UV_THREADPOOL_SIZE`, the processes a `stim` command starts inherit 16. A Windows service task written by `stim service install` sets `UV_THREADPOOL_SIZE` to 16 unless `--env` gives another value; an installed task gets it on its next `stim service install`. [6951f242f1](https://github.com/appandflow/stim/commit/6951f242f168e50fb6008ad709f02bb56de94aef) [163dbcde7b](https://github.com/appandflow/stim/commit/163dbcde7b6ae0bba55caa5aed5ee382948260b1)
- The daemon's dormant pass removes the build outputs (such as `android/app/build`) of an idle workspace root that has a workspace record but no registered project, for example a linked worktree whose app registration was lost. `stim gc` already removed them. [3f75ecadbe](https://github.com/appandflow/stim/commit/3f75ecadbe7e0a275e5a11edb9122afbb57e78d2)
- A simulator or emulator that the idle stage shut down and that a tool outside Stim boots again is kept for one idle window instead of being shut down again on the next tick. The daemon log and the workspace timeline record it once as `device_booted_after_idle`. Under memory or disk pressure the window does not apply, and the device cap's reclaim for a waiting Stim run is unchanged. [8bbc78ca6d](https://github.com/appandflow/stim/commit/8bbc78ca6d4b6918a0caa98aa770ad606711cb6c)
- A build worker removes the build areas of a client whose build access was revoked, or whose record a fresh setup of the same key replaced, at its next eviction pass, also when its stimd ran no job for that client. They used to stay forever. A live job, a claim or a device ledger still keeps them, and folders orphaned before this release are not removed automatically. [8c0e04d0b6](https://github.com/appandflow/stim/commit/8c0e04d0b6f53fe7e9a06179e2341f7b5fb5410f)
- A build worker declines a fresh build while any live holder, shared or exclusive, holds the claim on that checkout's build area, so the client places the build on another worker before syncing its source. An exact artifact hit is still taken. [bd18559306](https://github.com/appandflow/stim/commit/bd18559306e58bb8bfc556f568caaa2a91a75e0c)
- `stim settings unset` removes a retired 1.x key such as `devices.reclaimIdleMinutes` or `remote.buildMode` from every layer that holds it, or from the one named with `--scope`, instead of refusing it as `not a Stim setting`. [a7415fc400](https://github.com/appandflow/stim/commit/a7415fc400ac6a2c02187fa4934065fc2ee3500b)
- A supervised service with no `ports` and no `ready` command must still run one second after it starts. A start that exits within that second fails with `STIM_SERVICE_FAILED` and its log tail instead of being reported started. [90190a16bd](https://github.com/appandflow/stim/commit/90190a16bd84e3acfa703f201e38c3165d47b474)
- `stim worktree remove --force` prints, on stderr, each service whose teardown failed with the command to run by hand. `stim test` run from a monorepo root no longer prints a note that the folder is not a React Native or Expo app. A start that finds a service already running clears an earlier teardown failure from `stim services` and `stim status`. [a6e4e5e6dc](https://github.com/appandflow/stim/commit/a6e4e5e6dcbf8a919f2b5b6496adaee629c5f87f)

A worker's prebuild failure points at `stim logs --source build` or `--remote-build local` instead of pairing and build access. ## Migration notes

- **Rolling back to an engine before 2.0.0-rc.6 after the `.noindex` rename.** That engine starts the Metro cache and ccache cold under the old names, reaches the compilation cache warm through the link, and does not measure or trim the `*.noindex` folders. On workspace removal it checks only `agent-device/daemon.json`, so stop agent-device sessions before rolling back. [9cc203f737](https://github.com/appandflow/stim/commit/9cc203f7376a7ff7d1e2dc43f69947320b098ae1)

For upgrade steps, see the [Stim 2.0 upgrade guide](https://stim.appandflow.com/docs/migrate-to-2).
