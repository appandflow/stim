# 1.28.0

Stim Desktop and the Stim phone app ship through their own workflows; this release covers the twelve npm packages (`@stim-cli/core`, `@stim-cli/cache`, `@stim-cli/cache-s3`, `@stim-cli/agent-driver`, `@stim-cli/agent-driver-agent-device`, `@stim-cli/metro`, `@stim-cli/expo-build-cache`, `stim`, `@stim-cli/ci`, `@stim-cli/transport`, `@stim-cli/transport-tailscale` and `@stim-cli/server`). No package publishes for the first time in this release. Commits that only changed those apps, design documents or repository automation are not listed: [#4342](https://github.com/appandflow/stim/pull/4342) (the load-aware admission control design), [#4447](https://github.com/appandflow/stim/pull/4447) (the Load item and capacity meters in Stim Desktop and the phone app) and [#4457](https://github.com/appandflow/stim/pull/4457) (a scheduled workflow that releases stale issue claims).

## New

- **Hosted iOS and Android Debug runs carry Metro over connections the client opens.** The worker no longer connects back to the client: the client's Metro supervisor keeps four idle authenticated `device-host` connections per hosted session, and the worker's loopback bridge pairs each connection the hosted simulator or emulator makes with one of them. A worker shared into your tailnet with Tailscale device sharing, or one your ACLs only let you reach on its stim-server port (`:7443`), now runs hosted Debug builds; before, the run launched and then reported `launch UNVERIFIED: no bundle request reached this workspace's Metro`. The client no longer listens on its tailnet address. The worker holds at most 16 idle links per session, pings them every 15 s and closes the oldest past the limit. When every link is lost, for example across a stim-server restart, the supervisor stops reporting `ready` and the next `stim ios`, `android` or `reload` opens a fresh set. stim-server's hello rewrites the clients registry at most once a minute, so `lastSeenAt` is refreshed at that rate. The client and the worker must both run 1.28.0; see the migration notes. Fixes [#4449](https://github.com/appandflow/stim/issues/4449). (`stim`, `@stim-cli/core`, `@stim-cli/server`) [1e780deed](https://github.com/appandflow/stim/commit/1e780deed07bba8356f58adc74cc89ce116937d9)
- **`stim status` shows this Mac's load and slot usage.** Status always prints a `load 0.7/core (busy at 2)` line, and `status --json` gains `capacity.load`: `cpus`, `loadPerCore` (the 5-minute load average divided by `cpus`), `busyAt` (`server.maxLoadPerCore`), `limit` and `state` (`free` or `busy`; `limit` is `null` and `state` is never `holding` until a setting sets the limit). While `concurrency.maxBuilds` or `concurrency.maxDevices` is set, status prints `builds 1/2` and `devices 6/6` lines naming the holders, and `--json` gains `capacity.builds` and `capacity.devices` with `max`, `inUse` and `holders`; `capacity.devices.inUse` is `null`, with `unknown` saying why, when the devices could not be listed. These lines also print on a machine with no registered projects, such as an offload-only worker. In `status --watch --json`, `capacity.load` keeps its value until `loadPerCore` moves by 1 per core or `state`, `limit`, `busyAt` or `cpus` changes. Each `builds.ndjson` record gains `loadPerCore` at the start of the run and `boot: { startedAt, loadPerCore }` for the run's first owned simulator or emulator boot. Part of [#3919](https://github.com/appandflow/stim/issues/3919) and [#4337](https://github.com/appandflow/stim/issues/4337). (`stim`, `@stim-cli/core`) [6386dc2ba](https://github.com/appandflow/stim/commit/6386dc2baadfb2b2262fb671e7dd8109b2f006f9)

## Removed (breaking)

- **The client Metro gateway of hosted Debug runs.** `@stim-cli/core` no longer exports `createMetroGateway`; it exports `createMetroLinks` and the `MetroLink` and `MetroLinks` types beside `createMetroBridge`. `device-host.metro.open` no longer takes `gatewayPort` or `secret`: stim-server 1.28.0 refuses a request that carries them with `protocol-unsupported` and "Update stim on this machine, then retry.". The new `device-host.metro.link` method and the `hosted-metro-link` hello feature replace them. (`@stim-cli/core`, `@stim-cli/server`, `stim`) [1e780deed](https://github.com/appandflow/stim/commit/1e780deed07bba8356f58adc74cc89ce116937d9)

## Fixes

- **A worktree locked with `git worktree lock` is never lightened.** `gc --delete`, `gc --older-than`, the disk budget and automatic maintenance at every disk pressure level cleared the build outputs, in-tree build directories, `node_modules` and `ios/Pods` of an idle locked worktree, so a locked rollback checkout failed at launch with a missing module. They now keep everything in a locked worktree and name the lock in the report, the maintenance log and `gc --json` (`reason: locked` in `workspaceBuildOutputs`). A workspace whose project is inside a git checkout that git cannot list is kept too, with code `lock-unknown`. Fixes [#4444](https://github.com/appandflow/stim/issues/4444). [94cfd525b](https://github.com/appandflow/stim/commit/94cfd525bf7b281aacb83b56c140b458a838c659)
- **Ctrl-C during a hosted launch readiness wait cancels it.** The hosted iOS and Android launch paths did not pass the run's cancellation to Metro verification, so the wait could hang and wrote no cancelled run record. It now ends with `STIM_CANCELLED` and a cancelled build ledger row, as a local run does. Fixes [#4404](https://github.com/appandflow/stim/issues/4404). [7ea9bbda0](https://github.com/appandflow/stim/commit/7ea9bbda0530253665c3fe8542b6dbafd03c2bab)
- **Stopping a hosted macOS session ends every running copy of its app.** Each app delivery to a hosted session gets its own bundle with the same bundle id, and stop only looked for running copies under the workspace's `macos/` directory. A copy LaunchServices started from an earlier delivery, for example through `agent-device open <bundleId>`, kept running after `stim stop` deleted its bundle, and a later session on the same slot could resolve to it. The worker now stops every verified process running from one of the session's app bundles, before the bundles are removed and before a replacement launch; a copy that will not exit leaves the session `unknown` and its bundles in place. This runs in the worker's stim-server. Refs [#4127](https://github.com/appandflow/stim/issues/4127). [0d5153f45](https://github.com/appandflow/stim/commit/0d5153f45e6f3402c1a0cc7a7ab0a5f20de3a3da)

- **A Windows client takes an offloaded build's cache hit.** Windows `tar.exe -tf` ends each member name with CRLF, and the archive check split the listing on LF only, so every name kept a trailing carriage return and a valid app archive was rejected as containing paths outside its app. The listing is now split on LF or CRLF. Fixes [#4431](https://github.com/appandflow/stim/issues/4431). [753a7f949](https://github.com/appandflow/stim/commit/753a7f949ebb63d76abd27dedfe25907aaa4bacd)

## Docs

- **Which gestures a hosted macOS app lease refuses.** `stim guide macos` and the macOS website page say that `longpress`, `swipe`, `back` and other gestures not listed are refused under a `macos-app` lease, that the `longpress` and `swipe` in `stim guide lifecycle` are for hosted Android and iOS, and that `click --button secondary` reaches agent-device but its native macOS backend answers `UNSUPPORTED_OPERATION`, so a hosted macOS app has no right click yet. Fixes [#4452](https://github.com/appandflow/stim/issues/4452). [0abaef364](https://github.com/appandflow/stim/commit/0abaef3644d023a43a25842a515441404096274b)
- **A hosted macOS app screenshot can show macOS 27's sharing indicator.** `stim guide macos` and the macOS website page describe the symptom (a 66x20 point capture; `snapshot -i` lists an `axdialog` named "Window" with a `WindowSharingSessionButton` before the real window), link [callstack/agent-device#3961](https://github.com/callstack/agent-device/issues/3961), and say to read the UI with `agent-device snapshot` until agent-device selects the app's main window. Commands that use the front window's frame, such as `scroll`, can target the indicator too. Refs [#4123](https://github.com/appandflow/stim/issues/4123). [148cf45b3](https://github.com/appandflow/stim/commit/148cf45b361282ffa5713dba889d4460362d6599)

## Migration notes

- **Update the client and every hosting worker to 1.28.0 together for hosted Debug runs.** A 1.28.0 `stim` refuses a hosted iOS or Android Debug run on a worker whose stim-server lacks the `hosted-metro-link` feature, before it reserves a device. A 1.27.0 `stim` that asks a 1.28.0 stim-server for Metro gets `protocol-unsupported` with "Update stim on this machine, then retry.". Update every Mac that hosts simulators or emulators for other machines with `stim-server service update --release 1.28.0`, and update `stim` on each client. Linux and Windows workers take Android builds only and host no devices, so this does not apply to them. Release and other non-Debug hosted runs do not use Metro and are not affected. After updating, a worker no longer needs any network path to the client.
- **Restart a Metro supervisor started by 1.27.0** with `stim stop; stim start` in that workspace before the next hosted Debug run; until then the run refuses with that remedy.
- **Build offload is unaffected.** `STIM_BUILD_COMPAT` stays 2: `scripts/build-compat.json` was re-recorded for the build ledger fields without a bump, because those edits only record the run. A 1.27.0 machine and a 1.28.0 machine still offload builds to each other.
- **The hosted macOS fixes run in the worker.** The stop of every running copy of a hosted macOS app reaches a worker only after `stim-server service update --release 1.28.0` there.
- **Hosted macOS apps have no right click, and their screenshots can show the sharing indicator.** Under a `macos-app` lease, `click --button secondary` and `agent-device screenshot` depend on agent-device. Right click needs an agent-device release that includes [callstack/agent-device#3962](https://github.com/callstack/agent-device/pull/3962); the screenshot that returns macOS 27's window-sharing indicator instead of the app window ([callstack/agent-device#3961](https://github.com/callstack/agent-device/issues/3961)) needs one that includes [callstack/agent-device#3965](https://github.com/callstack/agent-device/pull/3965). Neither is released: the latest agent-device is 0.21.31. Read the app's UI with `agent-device snapshot` until then.
- **New fields, no new state files.** `status --json` gains `capacity.load`, and `capacity.builds` and `capacity.devices` while a cap is set; build ledger records gain `loadPerCore` and `boot`. All are optional, so older readers ignore them.
- **Stim Desktop 0.2.9 needs this release** for its Load item and its Devices and Builds meters, which read `capacity` from `stim status --json`. With an older `stim` they do not appear.

## QA

The maintainer authorized a stable release without the pre-tag QA gate on 2026-10-26, as for 1.16.0 through 1.27.0. This deviates from RELEASE.md section 3, which has no waiver for a stable version; the expedited RC lane is for prereleases only and was not used. The waiver covers only section 3. No section 3 QA round ran on any commit since v1.27.0, so no change in this release has been through QA, including the client-opened hosted Metro links, the load and slot usage in `status`, the build ledger's load fields, the locked-worktree rule in gc and maintenance, the hosted macOS stop and the Windows offload cache hit.
